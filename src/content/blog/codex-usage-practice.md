最近非常青睐使用 Codex：一方面是它的订阅配额比同类工具更加人性化；更重要的一方面是，作为 Mac 用户，Codex 桌面端提供了非常顺手的原生体验。

## 高频功能：Skill 与定时自动化

先说几个我日常用得最多的能力。

首先是 **Skill**。虽然这个概念已经老生常谈，但 Codex 在工程契约上走得更远，能够比较稳定地调用原生 Computer Use 等能力。我把很多日常信息整理做成了日报类的 Skill，再配合定时**自动化**（Automation）在固定时间点触发，最后通过自己写的一个本地 Web 工具（包括现在写这篇 Markdown 所用的本地编辑器）集中查看，每天早上打开就能很舒服地浏览完。除此之外，在内置浏览器里直接做前端批注修改、或者用 `/goal` 跑长周期任务，体验也都很不错。

## 工程化落地：分支契约、文档与 Worktree

对程序员来说，怎么把 Coding Agent 真正纳入可控的工程研发流才是最核心的问题。我的做法比较直接，核心是靠硬性的仓库契约把流程锁死：

1. **用 `AGENTS.md` 固化分支与目录契约**：单人维护的项目里，分支策略优先追求高吞吐与低心智负担，所有分支规范、构建测试命令都明确写进 `AGENTS.md` 让 Codex 严格遵守。同时在仓库内划分 `plan/` 与 `doc/` 目录：前者存放待开发的特性规划，后者维护精确到具体模块与文件的架构文档。
2. **项目初期长 Session 保持上下文连贯**：在项目刚起步、设计思路最密集的阶段，我会尽量在同一个长 Session 里把核心骨架搭完，而不急着频繁重开会话。初期大量的隐性假设和权衡留在完整上下文里，远比中途压缩成二手摘要更可靠。
3. **平稳期切换多 Worktree 并行**：当架构边界稳定、`plan/` 中的设计意图和 `doc/` 中的模块契约都已经清晰落盘后，再切到 Git Worktree 模式并行推进。因为分支规则、PR 提交流程和文档契约都已经对 Agent 透明，Codex 在多 Worktree 下的隔离开发就会非常顺畅。
4. **PR 自动多轮 Review 闭环**：我会配置一个专门用于代码审查的 Skill，在每次提 PR 后自动触发，并配合 10 分钟粒度的定时轮询任务：先核实 Review 指出的问题是否真实存在、修复是否会越界，确认无误后执行修复并再次触发 Review，如此循环直到不再报出新问题。之所以必须多轮触发，是因为模型的奖励机制往往让它单次只挑出三四个最显眼的问题就停下；如果遇到影响面较大的重构 PR，单靠一次扫描根本抓不全潜在缺陷。

在这个闭环之上，再把 CI/CD 的测试、构建和部署规则一并写进 `AGENTS.md`，整套日常开发流就基本能自洽运转了。

## 当前感知的短板

实际高频用下来，Codex 也还有不少明显的短板：

- **移动端远程连接体验粗糙**：App 端的线程与状态同步抽象做得不够扎实，远程控制时能明显感觉到手机端和桌面端像是在操作两套割裂的状态层，导致手机端小 Bug 频出。目前我在手机上基本只用来看一眼进度，不会指望用它替代桌面端干活。
- **设计稿与原型工具集成薄弱**：与 Figma、Pencil 等设计工具的衔接还不成熟，本质上是模型在原型结构与视觉规范上的训练数据与反馈闭环还不够充分。
- **前端审美与自由发挥不稳定**：如果缺乏明确的视觉 Token 和布局约束，让模型自由发挥改前端样式，往往越涂改越杂乱。
