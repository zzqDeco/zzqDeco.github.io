一个编程助手最危险的错误，不一定是写出立刻报错的代码。更难发现的情况是：它说某个函数存在，其实只是在名称上合理；它说测试通过，实际运行的是修改前的工作树；它说已经读过文件，读到的却是压缩过的片段；它说另一个 Agent 验证过，另一个 Agent 只是复述了实现者的总结。表面上，这些回答都像工程沟通，实际却缺少把声明接到外部事实的那一段链路。

本文以独立分析仓库 [how-claude-code-works](https://github.com/Windy3f3f3f3f/how-claude-code-works/tree/f4d6505ed9162a0ee6be089190f74c419ecacb19) 为主要阅读对象，结合 Anthropic 官方文档，研究 Claude Code 在这条链路上的设计。这里的“减少模型幻觉”是一个分析视角，不是官方宣布的单独产品模块，也不是本文测量得到的性能结论。我们要理解的是：哪些机制让模型更容易接触事实，哪些检查可以直接拒绝不满足前置条件的动作，哪些流程只是提醒模型，以及哪些可靠性要求最终必须由项目自己的测试和验收系统承担。

全文采用四种证据标记：**官方文档确认**表示官方对公开行为的说明；**社区快照分析**表示目标仓库对历史实现的分析；**社区黑盒观察**表示仓库作者通过运行行为、公开字符串或其他外部材料推断的机制；**本文工程推断**表示从上述材料提出的解释、反例、形式化和设计建议。后两类绝不自动升级成当前产品的实现事实。本文没有运行 Claude Code，没有读取私人会话，没有提取客户端内部内容，也没有调用付费模型开展对照实验。

先给出核心判断：**一个更可靠的 Agent，不是每一步都更有自信，而是更少在缺证据时继续扩大结论；当它已经作出错误判断时，系统还应有机会通过接口、状态和验证结果把它纠正回来。** Claude Code 的工具、编辑前置检查、上下文管理和扩展点，为这种设计提供了具体案例；它们也同时揭示，模型推理与工程验收之间始终存在不能用提示词填平的距离。

## 1. 读者导读：可靠性来自什么

### 1.1 不把模型和运行系统混为一谈

用户在终端看到一个回答，背后至少有两类不同的机制。模型根据当前上下文生成下一段文字或下一次工具调用；运行系统决定工具是否存在、参数是否合法、权限是否允许、如何执行操作，以及把什么结果交回模型。前者主要是统计推断，后者包含大量普通程序逻辑。讨论“Claude Code 为什么比较可靠”时，如果把这两类机制都归功于模型，就无法判断一个保证究竟来自哪里，也无法知道迁移到自己的 Agent 时应该复制什么。

例如，模型愿意先读文件，是行为选择；编辑工具拒绝在缺少读取记录时修改现有文件，是某条执行路径上的前置检查；测试运行器发现返回值错误，是独立于编辑动作的验证；用户确认需求已经满足，则是更外层的业务判断。这四件事可以形成配合，却不是同一种保障。模型可以忘记读取，工具也可能有其他写入路径，测试可能覆盖不足，用户也可能只看到漂亮的演示。因此，我们需要逐层分析，而不是寻找一个名叫“防幻觉”的万能开关。

### 1.2 这篇文章的阅读对象

主资料是一个教育性架构分析仓库，不是完整的官方 CLI 源码。本文阅读的是其中的结构图、实现摘录、机制描述、版本说明和作者纠正记录。官方文档用于核对公开行为，而不是为社区描述中的每一个函数背书。这样的证据组合很有价值：社区材料能提出具体问题，官方接口能帮助限定可依赖的行为，工程反例则用于检查结论有没有越过证据。

阅读时可以持续追问三个问题。第一，某个信息是模型猜的，还是工具真正观察到的？第二，一个动作是被建议不要做，还是会被程序拒绝？第三，一个结果是被描述为成功，还是有与当前交付物对应的外部检查？这三个问题分别指向事实来源、约束强度和完成条件。它们比“是否用了多 Agent”“上下文是不是很长”更接近可靠性的核心。

对应用开发者而言，本文的重点是证据如何进入工作流；对 Agent 平台开发者而言，重点是工具契约、状态记录和验证扩展点；对日常使用者而言，重点是识别哪些输出可以直接采信，哪些还需要要求模型重读、运行或明确标为未验证。本文不要求读者知道全部 Claude Code 内部符号，但默认读者理解文件编辑、测试、版本控制和基本工具调用。

### 1.3 三条贯穿全文的判断原则

第一条原则是**观察不等于理解**。读取文件能证明某些字节进入了工具结果，不能证明模型正确理解其调用关系；看到一个测试函数，不能证明它真的被测试命令收集。第二条是**执行不等于效果**。命令完成、文件写入、请求返回，都只是某个阶段的事件。第三条是**效果不等于完整交付**。单元测试通过，可以支持局部行为结论，却不能自动支持部署、权限、跨系统集成或业务验收。

这些原则不是要求每次任务都做无限验证。一个只改错别字的任务不需要启动整套分布式环境；一个改变授权边界的任务却不能只看格式检查。正确方向是让验证强度随风险和影响范围变化，并让最终报告准确表达已经覆盖的范围。省略不必要的检查可以是合理决策，但把没有执行的检查写成通过，不是优化，而是证据错误。

最后，本文把“减少幻觉”理解为降低无依据声明和错误行动的机会，而不预设改善幅度。架构分析可以解释机制为什么可能有效，不能代替控制变量实验。即使某个系统有精细的执行约束，也仍然可能在需求理解、算法设计、外部信息选择和验收范围上出错。对这些未被程序直接检查的部分，诚实的不确定性比包装成全面成功更重要。

### 2.2 证据标记怎样使用

后文的“社区快照分析”不是贬义，也不是默认不可信。它表示读者需要知道证据经过了一次转述。一个描述越接近公开可检验的输入输出，例如参数格式、错误类别或工具生命周期，就越容易交叉核验；一个描述越依赖未独立读取的内部源码、隐藏开关和实验默认值，就越需要谨慎限定。证据等级与结论是否有用是两个维度，不能简单按来源名气决定真伪。

“本文工程推断”则承担另一种职责。我们可以从读取与写入之间的时间差推导并发风险，可以从摘要压缩推导信息丢失风险，也可以设计更严格的验证合同。但这些推导不能被回写成产品已经实现的功能。全文的时序图、指标和案例中，凡是为了讲清问题而自行构造的内容，都会明确说明，而不是用一段看似真实的终端日志制造实测印象。

特别需要警惕同一句话内部的证据跳跃。例如，“工具采用字符串替换”可能来自具体实现分析，“因此模型必须理解整个代码结构”却是解释性推断，而且推断并不成立。唯一锚点可以通过复制一段相邻文本得到，完全不要求正确理解业务。阅读技术分析时，最重要的工作之一，就是把前半句的事实和后半句的评价分开。

目标分析仓库采用 MIT，本文引用其十张 Mermaid 图并保留来源和许可，附录收录对应版权声明。该许可适用于仓库作者有权授权的材料，不能被解释为 Anthropic 产品、商标、内部提示词或其他第三方内容全部转为 MIT。本文不会因为某段历史提示词出现在分析文档里，就再次整套复制。我们只短引必要术语、改写机制，并给读者可核对的文档位置。

仓库中的 `assets/architecture.png` 是文档网站截图，而不是产品内部架构图；本文因此不把它当成技术证据，也不使用人物照片或群二维码。十张原图都来自固定提交的 Mermaid 代码，四张额外图则是本文整理。原图里的历史说法如果需要限定，会在紧邻正文解释，不能为了让论点成立而悄悄删掉原图中的节点。

这些边界也决定了全文的置信度：对“本文实际阅读了什么版本的文档”置信度高；对官方当前公开接口的描述，以对应文档范围为准；对社区内部机制，保持二手分析身份；对某个机制到底能降低多少错误，目前没有本文实验支持。把这四种判断写清楚，正是本文所倡导的证据纪律在写作中的应用。

## 3. 究竟什么叫幻觉

### 3.1 先把错误拆开

编程任务里，“幻觉”常被用来指任何不符合预期的结果，这会妨碍设计有效防线。一个不存在的函数名是事实性错误；一个存在的函数被错误调用，可能是接口理解错误；正确调用却没有满足用户目标，是需求或设计错误；执行危险命令则涉及授权和安全。它们可以同时出现，但应该用不同的证据和测试诊断。否则，一个权限拦截器成功阻止了危险命令，也可能被误算为模型事实准确率提高。

本文主要关心两类直接与事实有关的失败。其一是模型输出没有依据的内容，包括不存在的文件、错误版本的 API、错误解释工具结果。其二是模型对行动与状态作出不真实的声明，例如没有运行测试却说通过，命令还在执行却说完成，读过旧文件却把结论描述为当前事实。后一类往往不会被普通代码编译发现，却会直接影响人的后续决策。

| 错误类型 | 典型表现 | 首要证据 | 容易混淆的情况 |
| --- | --- | --- | --- |
| 对象虚构 | 文件、类、工具不存在 | 仓库、工具目录、依赖接口 | 动态生成对象未被搜索覆盖 |
| 版本错配 | 用了另一版本的方法 | 锁文件、安装包、版本文档 | 同名接口跨版本语义改变 |
| 结果误报 | 日志失败却报告成功 | 原始输出、退出状态 | 部分步骤成功、整体失败 |
| 状态过期 | 旧检查支持新工作树 | 内容指纹、时间和依赖 | HEAD 不变但文件已修改 |
| 无依据完成 | 未检查就宣布交付 | 验收项与执行记录 | 实现完成但验收尚未完成 |
| 普通逻辑缺陷 | 边界条件算错 | 测试与运行行为 | 错误未必包含虚构事实 |
| 需求误解 | 做对了另一件事 | 用户要求与验收标准 | 产品目标本身尚不明确 |
| 越权动作 | 正确执行未授权操作 | 授权记录和权限策略 | 结果正确仍可能不可接受 |

### 3.2 事实有时间、范围和对象

“测试通过”不是一个完整事实。至少还需要知道测试哪个目录、使用什么参数、针对哪些修改、依赖环境是什么、是否收集到测试，以及退出状态如何。一句没有这些限定的成功陈述，在很小的任务里可能被共同上下文补全，但在长会话、多 Agent 和跨环境工作流中，省略的部分恰好最容易错位。

同样，“接口不存在”也需要范围。静态文本搜索没有命中，并不排除生成代码、运行时注入、导出别名或尚未安装的依赖；一个版本的文档没有出现某方法，不代表所有版本都没有。合理的回答应当是“在当前锁定依赖和已检查导出中没有发现”，然后决定是否继续验证。限定范围不是逃避结论，而是把结论绑定到实际证据。

状态性事实还有有效期。一份测试结果可能在写入新代码后立即过期，也可能在代码不变但环境配置改变后过期。相反，提交作者和历史 commit 内容通常较稳定。工程系统应该按照事实的可变性选择重查成本，而不是对所有内容采用同样策略。缓存一个历史设计说明和缓存“数据库已经迁移成功”，风险完全不同。

### 3.3 为什么定义会改变架构

如果把问题定义为模型不够聪明，解决方案通常是换模型、增加推理时间或要求自检。如果把问题定义为某类声明缺少外部依据，解决方案还会包括工具目录、版本化检索、读取记录、执行状态、结果校验和拒绝输出无证据结论。这并不否认模型能力的重要性，而是将它与其他可工程化的因素分开。

这种分解也影响故障复盘。对于虚构 API，应追问为什么没有读取当前依赖接口；对于旧测试冒充新测试，应追问结果为什么没有绑定内容；对于需求误解，应追问验收条件为何不明确。只写“模型幻觉了”既无法决定负责人，也无法形成可验证的修复。一个好的复盘应能指出哪条证据链断裂，下一次哪种检查可以提前发现。

最后，错误被工具拦截不等于模型没有产生错误。模型可能先生成非法调用，系统拒绝后再纠正。用户最终看到的答案更可靠，但模型原始输出的错误率并没有因此被直接测量。这是评价 Agent 时必须保留的区别：模型层面的错误、运行系统拦截的错误、逃逸到交付物的错误，是三个不同的统计对象。

## 4. 可靠性机制的五层分工

[![本文整理：证据、上下文、操作前置检查、执行验证与权限边界](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis01-reliability-layers.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis01-reliability-layers.webp)

*来源：本文整理，2026-10-27。此图是分析框架，不是 Anthropic 官方实现图。*

**图解决的问题。** 当人们把读取文件、系统提示词、权限提示和测试都称为防幻觉措施时，很容易忘记它们作用的位置不同。这张图把获取事实、使用事实、改变状态、验证效果和限制权限分开，便于判断一个失败需要在哪层处理。

**图中结构。** 用户目标先被转化为证据需求，观察结果进入上下文，模型提出操作，运行系统检查前置条件，再执行并交给验证器。权限边界横跨操作和执行，但不替代事实判断。验证不足时回到取证环节，而不是直接把任务标记为完成。

**支持的结论。** 可靠性是多处检查协作的结果。上游取证可以减少猜测，下游测试可以发现已经写入的错误，而结果报告负责防止错误状态被包装成成功。**不能证明的内容。** 这张图没有给出各层的实测贡献，也不意味着产品已经拥有所有建议的证据记录字段。

### 4.1 第一层：让模型接触当前事实

文件读取、代码搜索、依赖查询、文档获取和环境状态检查都属于这一层。它们解决的是信息缺口：模型不知道当前仓库有哪些模块，不知道依赖安装的准确版本，不知道某命令是否可用。有效取证的标准不是工具调用次数多，而是回答了足以影响决策的未知项。读取十个无关文件可能比读取一个关键入口更糟，因为它扩大上下文却没有降低决策的不确定性。

### 4.2 第二层：保持事实的来源和限定条件

工具结果进入上下文以后，仍可能被截断、摘要、排序、重写或遗忘。这一层关注证据是否还保留来源、时态、失败状态和覆盖范围。它不能靠无限扩大上下文解决，因为更多文本也可能造成干扰。更实际的方式是保留高价值证据的定位信息，允许按需重读，并在摘要不足时承认缺口。数据保留和模型可见性是两个问题：文件还在磁盘上，不等于模型在当前一步看到了它。

### 4.3 第三层：把部分错误变成可拒绝的调用

工具名称检查、参数类型检查、文件读取前置条件、锚点唯一性和状态新鲜度，能把部分错误从语言层转成程序判定。它们最有价值的地方是无需等模型自己意识到问题。但这种检查必须有明确谓词，例如“目标文本出现次数是否为一”，而不是模糊的“代码是否合理”。越接近语义正确性，越难通过通用前置条件保证，因此不能把入口校验的能力无限扩大。

### 4.4 第四层：验证实际后果

类型检查、测试、实际交互、差异审阅和业务验收在这一层。它们评估的不再只是调用格式，而是动作对系统造成的后果。一个检查是否有意义，取决于它能否区分目标行为与常见错误行为。如果测试只断言函数存在，就无法证明授权判断正确；如果界面检查只看页面返回二百状态码，就无法证明交互可用。验证器本身也需要设计和维护。

| 控制形式 | 谁作出判断 | 典型作用 | 不能保证 |
| --- | --- | --- | --- |
| 提示词与项目规则 | 模型 | 引导行为、表达约定 | 必然遵守全部规则 |
| 工具 Schema | 程序 | 拒绝格式或类型不符 | 参数语义正确 |
| 状态前置检查 | 程序 | 限制基于过期状态的动作 | 全局并发一致性 |
| 模型审查 | 另一次推断 | 发现部分推理与实现问题 | 独立、无偏、穷尽 |
| 测试与类型检查 | 程序及测试规格 | 验证已编码的性质 | 未写入规格的需求 |
| 人工验收 | 授权的人 | 判断业务与风险接受度 | 永不遗漏问题 |

### 4.5 第五层：限制影响范围

权限、沙箱和人工批准主要限制可以做什么，以及做错后影响多大。它们与减少幻觉可以协作，却没有相同目标。一个只读 Agent 仍能给出错误解释，一个受限写入工具仍能生成错误算法。反过来，一个完全正确的数据库删除操作也可能未经授权。把这两条轴分开，才能在事故后判断是知识问题、判断问题还是权限问题，并避免用某一层的成功掩盖另一层的失败。

## 5. Agent Loop：把回答接到外部世界

[![仓库原图：QueryEngine 与 query 的双层生成器架构](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo01-agent-loop.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo01-agent-loop.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/02-agent-loop.md, 双层生成器架构, MIT. 非官方历史实现分析图。*

**图解决的问题。** [主循环专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/02-agent-loop.md)试图解释一次用户请求为什么会产生多次模型调用和工具执行，而不是一次性生成最终答案。**图中结构。** 外层处理用户输入与会话生命周期，内层组织模型响应、工具结果和继续执行条件。图里的函数名称是仓库报告的历史实现位置，不是本文直接核对过的官方当前源码。

**支持的结论。** 工具反馈可以改变下一轮决策，使错误假设有机会被实际结果修正。**不能证明的内容。** 有循环不等于一定使用了有效证据，也不意味着循环会自动收敛到正确答案；错误观察、无效重试或错误终止条件都可能在循环中累积。

### 5.1 一种用于讨论的形式化

下面的表示是本文整理，而非原仓库提出的数学模型。令 $S_t$ 表示运行状态，$C_t$ 表示第 $t$ 次模型调用实际可见的上下文，$a_t$ 表示拟议动作，$o_t$ 表示工具观察：

$$
C_t=P(S_t),\qquad a_t\sim\pi_\theta(\cdot\mid C_t),
$$

$$
o_t=\operatorname{Execute}(a_t,S_t),\qquad
S_{t+1}=U(S_t,a_t,o_t).
$$

$P$ 很重要：它表示完整会话状态到模型上下文的投影。完整日志、磁盘文件和后台任务状态未必全部进入模型窗口。$U$ 也不仅是把一段文字附在末尾，它还可能更新工具状态、任务状态和持久化记录。理解这两个位置，才能看到为什么上下文压缩和结果记录会直接影响可靠性。

### 5.2 观察应当改变判断

设模型最初认为项目使用某个测试框架，搜索配置后发现并非如此。一个有效循环应该修正测试命令，而不是把新观察仅当附加文字继续原方案。这里有两个失败点：工具结果是否明确呈现差异，以及模型是否正确更新假设。前者可以通过结构化错误和清晰输出改善，后者仍依赖推理能力。运行系统的职责，是尽量不让失败被隐藏成空输出或笼统成功。

同样，工具调用失败以后，继续执行不一定合理。路径错误需要重新定位，权限拒绝需要尊重边界，瞬时网络错误可能允许有限重试，参数不符合接口则需要修改调用。把所有错误都当作“再试一次”会浪费预算，还可能在有副作用的工具上造成重复写入。主循环应该保留错误类别，而文章读者也应区分纠错、重试和绕过限制这三件事。

### 5.3 工具结果的时间语义

异步命令返回一个会话标识，意味着执行已开始，不意味着已经结束。一次构建可能先打印成功编译若干模块，最后却在打包阶段失败；一个部署请求可能返回受理状态，实际发布仍在排队。模型如果只看到早期正面消息就结束任务，产生的是行动状态幻觉。为避免这种错误，报告应绑定最终状态而不是最后一条看起来积极的日志。

工具结果还可能只覆盖局部。例如读取前两百行不能证明文件后半部分没有定义；查询第一页工单不能证明没有后续页；只获取标准输出可能遗漏标准错误。循环中的每一个观察都有边界，模型需要在扩大结论前补齐相关范围。系统能够通过分页标志、截断提示和显式状态帮助模型，但不能仅凭“使用了工具”就把后续推断视为可靠。

### 5.4 终止是一个独立决策

什么时候停止循环，与怎样选择下一次工具调用同样重要。用户目标可能要求交付代码、验证行为和说明限制三个结果，不能在第一个结果完成时就整体终止。另一方面，无限续跑也不是可靠性：如果环境缺失、数据不可访问或需求矛盾，应明确报告阻塞和已完成范围。可靠终止意味着有足够依据支持当前报告，而不是必须生成一个毫无保留的成功结论。

从这个角度看，Agent Loop 的贡献是提供了一个可反复接收外部反馈的结构。它没有神奇地改变模型的知识边界，而是让系统不必把第一次猜测当成最后答案。真正决定这个结构是否有效的，是后续章节中的工具契约、证据保存、错误处理和验证标准。

## 6. 先搜索再判断：用观察替代名称联想

### 6.1 编程知识不是当前仓库的地图

模型可以知道某种框架常见的目录结构，却不知道用户当前仓库是否遵循它。它可以知道某个库曾经提供一个方法，却不知道锁文件固定的版本是否包含该方法。训练知识在这里适合产生搜索假设，不适合直接充当事实来源。一个常见的可靠性改进，就是把“我推测这里应该有某函数”转换成“先定位入口、导出和调用者，再决定修改位置”。

Glob、Grep 和 Read 分别回答不同问题。Glob 根据文件名或路径模式缩小候选，Grep 根据文本模式定位内容，Read 提供判断所需的实际上下文。三者不能彼此替代：路径命中不说明文件内容符合预期，文本命中不说明语法作用域或运行时路径正确，而孤立读取某个文件又可能忽略真实入口。有效搜索通常是一组逐步收窄假设的动作，而不是一次大范围输出全部匹配。

可以用一个构造例子说明这种区别。用户要求修复日期显示，模型搜到 `formatDate` 后立刻修改，是基于名称相似作决定。如果项目同时存在服务端格式化、客户端本地化和历史兼容模块，真正产生页面内容的可能不是第一个命中。更可靠的做法是从路由或组件入口追到实际调用点，确认数据类型和默认时区，再阅读被调用实现。搜索提供候选，调用链提供因果关系。

### 6.2 负结果也需要解释

“没有找到”可能有多种含义：路径范围不对，大小写不匹配，文件被忽略，依赖不在仓库中，代码由构建生成，符号通过别名导出，或查询表达式本身错误。对于一个需要证明不存在的判断，单次文本搜索通常证据不足。模型应先检查搜索范围，再查看导出表、类型声明、包内容或运行时接口，而不是立即创建一个重复实现。

相反，搜索命中也不证明接口可用。README 中的示例、注释、测试夹具和弃用文件都可能包含同名方法；一个函数定义可能从未进入当前构建。判断是否可调用，需要同时确认包版本、导出路径、执行平台和类型约束。对于多语言仓库，还需要区分源代码、生成代码、接口描述与打包产物，避免把某一种表示中的符号直接搬到另一种环境。

这也解释了为什么搜索结果应保留路径和位置。把十个匹配行拼成没有来源的文本，会降低模型建立调用关系的能力。位置本身又不是永久标识，后续编辑会移动行号，因此长期记录更适合保留符号、内容片段和版本信息。行号方便人跳转，版本与内容才帮助判断证据是否仍指向同一个对象。

### 6.3 从最小充分证据开始

本文建议将探索分为三个阶段。先确定任务入口和约束，例如启动命令、依赖版本、测试位置；再沿实际数据流阅读关键模块；最后根据风险补齐边界条件和相关调用者。这个顺序能够让每一次读取回答明确问题。它比一开始把整个仓库塞进上下文更容易审计，因为读者可以解释“为什么看这个文件”。

这里的“最小”不是越少越好。如果任务改变共享接口，只看一个调用者可能导致其他模块回归；如果涉及授权，必须查看服务端执行点，不能只检查前端按钮。最小充分证据是相对于决策而言的：要足以区分当前候选方案和主要反例，又避免用大量无关内容掩盖关键约束。它需要随着调查发现动态调整，而不是固定文件数量。

从减少幻觉的角度看，搜索最大的贡献是把可以通过环境发现的未知项从语言推断中移走。但模型仍然需要判断搜索证据是否充分，因此工具设计应提供明确的截断、分页和范围信息。工具输出越像一份可定位的观察记录，模型就越不容易把“我看到的一部分”误写成“整个系统的事实”。

## 7. 工具目录、Schema 与执行入口

**图解决的问题。** [工具系统专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/04-tool-system.md)把模型输出与实际执行之间的处理过程显式展开。**图中结构。** 请求先经过名称查找、输入验证和权限相关处理，再执行工具、处理结果、触发后续 Hook 并返回消息。**支持的结论。** 工具调用不是把模型生成的任意字符串直接变成系统行为，中间可以布置程序检查。**不能证明的内容。** 图中的历史调用顺序、分类器和权限优先级不能直接当成当前版本的完整规范。

还需要纠正图中一处容易误读的文字：“Zod Schema 解析+强制”不能理解为 `safeParse` 自动对所有输入做类型转换。是否转换取决于具体 Schema 是否声明 coercion 或 transformation；普通数字类型不会仅因为调用了解析方法，就把任意数字字符串视为数字。本文保留原图，但不沿用这种笼统概括。参数处理必须以实际接口声明为准，参见 [Zod 官方 coercion 说明](https://zod.dev/api#coercion)。

### 7.1 名称存在性是第一道事实检查

当模型请求一个没有注册的工具，运行系统可以立即返回错误。这条检查的能力非常明确：它不判断模型想做的事是否合理，只判断当前工具池是否有这个名称或合法别名。它将一种常见幻觉变成了可观察失败，避免“工具名听起来合理”就被当作可执行能力。

别名与弃用又使问题稍微复杂。旧名称可能仍被接受，但同时返回提示，要求后续使用新名称；同一个连接器在不同会话可能暴露不同工具集合。模型因此不能只记住上一轮可用的名称，还要遵循当前工具目录。对于自己搭建的 Agent，工具发现结果最好能关联服务版本或目录版本，避免长会话在接口变化后继续使用过期知识。

### 7.2 类型合法不等于业务合法

Schema 适合检查字段、类型、枚举、长度和嵌套结构。例如路径必须是字符串，替换内容必须提供，模式只能从限定集合选择。这些性质在执行前就能判断，不需要模型再次解释。业务验证则可能需要读取状态：文件是否存在，资源是否归当前项目，旧锚点是否唯一，目标任务是否已经关闭。两层验证的职责不同，不应挤进一个“参数正确”的含糊状态。

一个完全合法的字符串可以指向错误文件，一个合法的整数可以是错误用户标识，一个符合格式的 SQL 可以查询错误租户。即使工具声明支持结构化输出，也只是收紧表达空间，不会自动给内容附上真实性。模型仍可能以合法格式表达错误意图，因此后续需要状态检查、授权判断和效果验证。

### 7.3 工具契约应该暴露哪些信息

从本文的工程视角，工具说明至少应区分读写性质、输入范围、结果含义、失败方式和重试条件。一个返回布尔值的工具，如果不说明它表示“已受理”还是“已完成”，会把误报风险转嫁给模型。一个写入工具如果在网络超时后不说明是否可能已执行，自动重试就可能造成重复副作用。接口越明确，模型需要自行填补的语义越少。

但工具说明也会占用上下文。为每个工具塞入大量背景知识，可能让模型更难选择正确工具。因此工具契约应优先写决定调用是否合法的约束，而把详细操作流程放在按需读取的文档或技能中。工具目录解决“现在可以调用什么”，业务流程解决“在什么情况下该调用它”，二者结合才有助于减少无依据行动。

## 8. 结构化错误：让失败成为下一步的证据

### 8.1 错误返回不是异常噪声

传统交互程序常把错误交给人阅读；Agent 系统则需要让错误成为下一次决策的输入。如果一个工具把不同失败都压成“操作失败”，模型就只能猜原因。相反，明确区分名称不存在、参数不合法、状态过期、权限拒绝和后端不可用，可以把恢复路径缩小到合理集合。社区分析所描述的工具结果与失败 Hook，提供了研究这种反馈通道的切入点。

不过，结构化不意味着一定要发明庞大错误码体系。关键是错误信息能否回答三个问题：动作有没有发生，失败是否可能暂时存在，下一步需要补什么证据。例如“锚点出现三次，尚未写入文件”比“编辑失败”更有价值，因为它既给出了定位问题，也说明没有产生部分副作用。模型可以据此扩大锚点，而不是盲目改用覆盖文件的方式。

### 8.2 三种不同的恢复动作

第一种是**修正调用**。参数缺失、类型错误、路径不对，需要改变输入。第二种是**刷新状态**。文件发生变化、任务版本不符、资源已删除，需要重新观察世界再作决定。第三种是**等待或升级处理**。网络故障、限流、服务不可用和权限问题可能需要等待、换可用数据源或请求用户补充授权。把三类情况区分开，可以避免以连续重试掩盖没有进展的事实。

重试本身还应受副作用约束。只读查询通常容易重试，创建资源、发送消息或执行迁移则需要幂等键、状态查询或明确的重复执行保护。一个超时并不证明服务端没有做事。本文不会把这些通用分布式系统要求都写成 Claude Code 内置功能，但它们直接说明：模型收到错误后的合理行为，依赖工具契约是否足够明确。

### 8.3 不把失败转换成漂亮的空结果

一种很隐蔽的错误是把“查询失败”当成“查询成功但没有结果”。例如依赖目录不可读，却回答“没有找到任何使用”；测试命令不存在，却把标准输出为空解释为“没有错误”；网络抓取到验证页面，却据此总结原文。这类问题不是模型凭空编造一个新对象，而是把工具失败误归类为负证据。

为了防止这种混淆，工具返回应保留状态与数据的分离。空集合可以是成功结果，也可以是失败后的占位，只有状态字段或可靠的执行上下文才能区分。模型报告应沿用这种区别：成功搜索且范围充分时，可以说没有发现；搜索未完成时，只能说暂时没有证据。这会使措辞略长，却能避免用户基于错误的“没有”作决策。

### 8.4 错误链条与停止条件

当一个 Agent 连续遇到相同错误，可靠行为不是无限变换命令直到某个命令不报错。它应检查自己是否一直使用同一个错误假设，或者当前环境根本不满足任务前提。例如缺少运行时，绕过启动命令改为静态搜索可以继续分析，但不能因此宣称实际行为已验证。错误恢复应该保留原验证目标，而不是悄悄把任务换成更容易成功的替代目标。

还有一种风险来自输出被过度修饰。把冗长堆栈压缩成摘要有助于节省上下文，但不能丢掉最终退出状态、失败阶段和关键环境信息。错误消息中也可能包含不可信文本或敏感数据，需要脱敏和来源标记。可读性与保真度并不冲突，前提是先确定哪些字段对下一步判断不可缺少，再压缩重复细节。

这类设计最终追求的是让失败可定位、可恢复、可报告。它并不要求系统避免所有工具错误，相反，明确的失败经常比模型自信地绕过问题更安全。真正需要避免的是错误在经过几轮转述后失去身份，最后变成“已经处理好了”的无依据结论。

## 9. Tool Search：少看工具，不是少定义工具

### 9.1 工具数量也是上下文问题

当一个会话接入大量工具，每个工具的名称、参数和描述都会竞争模型的注意力。工具越多，并不意味着选择越准确；相似名称、重叠功能和大量不相关说明可能增加混淆。按需发现工具的价值，是让当前决策看到较相关的一组接口，而不是要求模型始终在全部目录中寻找正确答案。

这与普通资料检索有相似之处，但检索对象是可执行能力。工具搜索的结果不仅是解释文本，还需要让模型知道能以什么 Schema 调用工具。因而它包含目录发现、定义加载和后续调用三个环节。搜索命中只完成了第一部分，不能跳过参数规范，也不能把检索结果里的任意名字都当成可信执行入口。

### 9.2 defer_loading 的准确语义

[官方 Tool Search 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)说明，调用方仍在请求的工具数组中提供工具定义，对延迟加载的工具设置 `defer_loading`；初始模型上下文只包含搜索工具和非延迟工具，命中后再展开相关定义。必须区分“发送给服务端”“进入模型上下文”和“已经实际执行”这三个时刻。延迟进入上下文不等于客户端根本没有传送定义。

目标分析仓库固定提交的提交说明，正是在修正这一点以及相关缓存表述。这个修订比一个抽象的“要核验来源”口号更有教育意义：即使整体分析很深入，某个接口机制仍可能被写错；新的官方说明或更精确理解会改变结论。本文因此采用固定提交，而不是将不断变化的 main 当成不变参考。

### 9.3 检索失误怎样影响工具调用

渐进加载也会引入新的失败路径。如果搜索描述没有覆盖工具能力，模型可能认为没有可用工具；如果用户问题被错误改写，搜索可能返回不合适的接口；如果目录更新而会话仍持有旧结果，后续调用可能失败。减少上下文负担并不等于消除工具发现风险，系统仍需保留重新搜索和处理未知工具的路径。

一个合理的使用策略是，在工具调用错误提示目录或名称发生变化时，回到发现步骤，而不是继续凭记忆修改工具名。对于高影响动作，还应在调用前重新阅读参数和副作用说明，因为“搜索到一个可以删除资源的工具”远远不等于用户授权删除当前资源。能力发现与授权判定属于不同阶段。

### 9.4 上下文节省不是正确性证明

工具定义更少，可能使模型更容易聚焦；但这种机制是否降低某类错误，需要在具体工具集和任务上测量。不能从上下文节省比例直接推导任务成功率，也不能把服务商的某一项工具选择实验外推为所有编码任务的幻觉下降。本文只采用可核对的机制解释，不借用无关数字给结论增加权威感。

同样，缓存主要解决重复输入的成本和时延。一个被高效缓存的错误说明仍然是错误说明，一个缓存命中的接口目录也可能已经不适合当前环境。上下文工程中有些设计直接改善证据可用性，有些主要改善资源效率，二者可能相关，但需要分别论证。把所有优化都归入反幻觉，会让系统分析失去区分度。

对自建 Agent 的启发是：应同时监控工具发现失败、加载后的调用失败和实际任务失败。只观察搜索命中率会高估能力，因为一个结果即使被找到，也可能不能被正确使用。完整链路应该从用户意图一直追到工具效果，而不是在目录检索这一中间阶段停止评价。

## 10. Read-Before-Edit：把读取变成前置条件

### 10.1 从建议到检查

[编辑策略专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/05-code-editing-strategy.md)报告，历史实现的文件工具在修改已有文件前检查 `readFileState`。如果不存在合适的读取记录，工具会要求先读取文件。这比单纯在系统提示词里写“修改前先阅读”更强：即使模型跳过步骤，特定工具入口仍能拒绝继续执行。

这里的限定词非常重要。本文说的是社区分析中的特定文件工具路径，不是所有操作系统写入方式，也不是经过实测的当前版本全局保证。新建文件原本没有可读内容，应与覆盖已有文件分开；不同工具的实现和权限也可能不同。只有把作用范围写清楚，才能理解这条检查实际能阻止哪些错误。

### 10.2 读取记录究竟证明了什么

读取记录可以证明运行系统曾经处理过某个文件的读取，并保存了相应状态。它可能帮助编辑器判断原文是否存在、模型看到的视图是否合适、文件是否发生变化。它不能证明模型读懂了文件，不能证明模型关注到了关键分支，也不能证明它把新读到的内容正确融合进方案。程序检查的是可观察事件，不是模型内部的理解质量。

这一区分解释了为什么读前约束仍然有价值。系统不需要证明理解完整，才能排除“从来没看过就覆盖”这一类明显高风险行为。许多工程保障都是局部的：类型系统不证明业务正确，却能排除某些类型错误；读取检查不证明语义理解，却能要求至少有一次基于真实文件的观察。局部保障的价值不应被低估，但也不能被扩大成整体保证。

### 10.3 一个用于解释的前置条件

为了分析，可以把一次编辑的部分必要条件写成如下谓词。它是本文抽象，不是 Claude Code 的原始函数签名：

$$
\operatorname{AdmitEdit}(p)=
\operatorname{ReadableObservation}(p)
\land\operatorname{FreshEnough}(p)
\land\operatorname{ValidAnchor}(p)
\land\operatorname{Authorized}(p).
$$

每个谓词都需要独立解释。读取条件回答有没有合适观察；新鲜度回答观察是否可能过期；锚点条件回答修改位置是否明确；授权条件回答是否允许执行。即使四项都满足，新代码仍然可能错误，因此它们只是准入条件，不是最终验收。把函数名写成 `CorrectEdit` 会产生误导，写成 `AdmitEdit` 更接近实际语义。

### 10.4 为什么要求读当前内容

模型可能在早先会话、记忆文件或训练知识中见过相似实现，但这些来源无法替代当前工作树。用户可能修改了函数签名，依赖升级可能改变返回类型，另一个任务可能已经完成部分修复。重新读取不仅为了生成能匹配的旧字符串，也为了避免覆盖用户尚未提交的改动。对协作环境而言，保存已有工作往往与修复当前问题同样重要。

读取还可以改变方案。如果原先假设需要新增模块，而实际代码已经有合适扩展点，读后应调整实现；如果发现需求涉及多个入口，就应扩大验证范围。一个机械执行“先读一次”的 Agent，仍可能完全照旧计划修改。因而工具层检查需要与行为层的假设更新结合，不能把通过前置检查当成完成探索。

### 10.5 设计上的收益与成本

读取前置条件增加工具调用和上下文占用，但通常能换来更明确的修改基础。对于巨大文件，需要结合局部定位和合适的读取策略，避免用一次全量输出造成新的截断问题。对于高频自动编辑，缓存读取状态可以减少重复工作，但缓存又必须考虑文件变化。这里不是简单的“每改一次都全读”规则，而是观察充分性、新鲜度和成本之间的工程平衡。

对自建工具来说，最值得迁移的不是某个内部字段名称，而是这条设计原则：如果动作依赖外部对象的当前状态，就让这种依赖出现在接口或执行器里，而不要完全寄托于模型记得先检查。这样即使模型出现遗漏，系统仍有一个可解释、可恢复的拒绝点。

## 11. 局部视图不等于磁盘原文

### 11.1 一份文件可能有几种表示

文件在磁盘上的字节、读取工具返回的文本、自动注入到提示词中的内容，以及压缩后保留的摘要，可能是四种不同表示。对模型来说，它们都像“看到文件”，但对编辑工具来说，只有某些表示足以支持可靠替换。例如自动注入的项目说明可能去掉注释或元数据，记忆入口可能只保留开头部分，网页抓取可能返回经过另一个模型处理的摘要。把这些表示都视为原文，会产生错误锚点和错误范围判断。

社区编辑专题将 `isPartialView` 与这种经过处理的自动注入视图联系起来。这个字段的意义不是“模型只要没读整个文件就永远不能改”，而是标记某些不能直接等同于磁盘内容的视图。尤其不能把它与普通 Read 的 offset、limit 参数机械画等号。历史分析中，后者还被用于判断是否适合做完整内容比较，是另一条判定维度。

### 11.2 为什么自动注入不一定算一次合格读取

设一个配置文件在磁盘上包含 frontmatter、HTML 注释和正文，自动注入时只展示正文。模型如果基于注入内容构造覆盖写入，可能无意删除元数据和注释；如果构造跨段替换，锚点也可能与磁盘不匹配。要求再次通过文件工具读取，是为了把模型观察与实际编辑对象重新对齐，而不是为了强迫多一次形式化工具调用。

还有一种更微妙的情况：缓存里保存的是磁盘完整内容，而模型看到的是处理后的视图。程序若只检查“缓存中有这个文件”，就会错把内部可见性当成模型可见性。一个可靠的状态结构需要区分保存了什么、展示了什么、展示范围是什么。对 Agent 平台开发者来说，这种区分很有借鉴意义，尤其是在自动摘要、脱敏和权限过滤普遍存在的系统中。

### 11.3 脱敏与保真之间的张力

并不是所有原文都应该完整交给模型。配置可能含凭据，日志可能含个人信息，工具输出可能包含与任务无关的敏感内容。系统需要做脱敏，但脱敏后的文本又可能不适合作为原样编辑依据。因此，脱敏视图应主要支持理解，写入操作则需要有不会误覆盖隐藏内容的接口，例如限定字段更新、带版本条件的补丁或由服务端完成的结构化修改。

本文不声称 Claude Code 已对所有这类场景提供统一解法。这里的推断是：当读操作和写操作使用不同表示时，必须明确二者的关系。否则，所谓“先读再写”会退化成形式上的事件顺序，无法防止隐藏字段丢失。这也是为什么某些系统更适合暴露业务级更新工具，而不是直接允许 Agent 覆盖整个配置文件。

### 11.4 局部读取怎样保持可靠

对于很长的代码文件，局部读取是合理的。模型可以先定位目标符号，再读取定义和必要调用上下文，而不必把所有内容装进窗口。关键是最终声明应与读取范围一致：理解一个函数的局部逻辑，不等于已经审计整个模块；替换一个唯一片段，不等于知道所有副作用。局部阅读需要配合调用链、接口和测试，而不是假装它等价于全量理解。

具体到编辑，较好的策略是保留足够定位上下文、避免不必要的全文件重写，并在修改后读取实际差异。若任务要求修改一个结构化配置项，使用解析后的字段更新比手工拼接大段文本更容易保留其他内容。若必须覆盖文件，应重新核对未修改区域，尤其是用户已有改动。这里的原则不是禁止某种工具，而是让观察范围与修改范围相匹配。

### 11.5 一个可迁移的表示合同

自建系统可以为观察增加“原始、脱敏、摘要、片段”这样的表示标签，并附带来源版本和范围。执行器据此决定哪些观察可以支持哪种写操作。标签并不证明内容正确，但能防止一种确定性混淆：用摘要冒充原文，用已处理文本冒充可直接覆盖的对象。这样的设计通常比继续增加提示词警告更可审计。

必须同时避免另一种过度设计：为每次简单读取引入复杂证明系统。合理的实现可以从高风险路径开始，例如覆盖配置、更新权限、批量修改和长会话接续。先识别表示不一致可能造成损失的地方，再决定记录哪些元数据，才能让可靠性成本与实际风险相称。

## 12. 锚点替换：明确位置，不保证正确理解

### 12.1 为什么选择旧文本作为定位依据

社区分析中的编辑接口以路径、旧文本、新文本和是否全局替换为核心。与让模型重新输出整个文件相比，局部替换可以减少无关内容变化，也让差异更容易审阅。旧文本既是定位条件，也是模型对当前文件的一种可检查陈述：如果它根本不在文件里，执行器就知道这个修改请求至少在定位上有问题。

下面是本文构造的接口形状示意，不是一次实际工具调用：

```json
{
  "file_path": "/workspace/src/date.ts",
  "old_string": "return format(value, defaultLocale);",
  "new_string": "return format(value, requestedLocale);",
  "replace_all": false
}
```

这个请求可能在格式上完全合法，但仍然有很多未知项：变量是否存在，调用者是否传入正确 locale，空值如何处理，以及默认行为是否应该保留。锚点检查只负责确认替换对象，不负责自动回答这些业务问题。因此，读者不应因为工具接受了补丁，就认为所有相关假设已经得到验证。

### 12.2 无匹配、多匹配与全局替换

无匹配通常意味着模型使用了错误片段、旧版本内容或经过处理的文本。合理恢复是重新读取和定位，而不是立即改用全文件覆盖。多匹配则意味着锚点不够明确，模型应增加上下文，或者在确有批量替换意图时显式选择全局替换。这里的显式性有价值：它把“所有出现位置都要改”从隐含猜测变成可以审阅的选择。

| 场景 | 定位检查结果 | 正确的下一步 | 不应得出的结论 |
| --- | --- | --- | --- |
| 没有旧文本 | 拒绝替换 | 重新定位当前内容 | 文件一定不存在 |
| 旧文本出现多次 | 通常拒绝单次替换 | 扩大上下文或明确批量范围 | 随便改第一处即可 |
| 唯一锚点存在 | 定位可继续 | 检查新内容和调用关系 | 模型已经理解业务 |
| 显式全局替换 | 允许表达批量意图 | 审查每种使用语境 | 文本相同就语义相同 |
| 编辑后无差异 | 没有实质修改 | 检查请求是否重复 | 问题已自动解决 |

同名文本可能出现在测试、注释、兼容分支和生产代码中。全局替换即使没有执行错误，也可能改变不应变化的语义。因此，批量操作通常需要更严格的范围控制和差异检查。一个词在文本层面相同，不代表它在程序中指向同一个符号；这也是语法感知重构工具与普通字符串替换的差别。

### 12.3 “精确”也要看具体匹配流程

分析仓库还讨论了引号处理、文本规范化和实际字符串查找。因而“精确替换”应理解为以旧文本为锚点的受约束编辑，而不是未经核对就承诺所有阶段都是逐字节比较。换行、编码、Unicode 引号和工具展示格式都可能影响匹配。对实现者而言，任何规范化都应有可解释的边界，否则方便纠错的容忍机制也可能扩大误匹配范围。

在文章层面，最重要的不是复述每一个历史辅助函数，而是理解设计取舍：完全严格的匹配容易因表示差异失败，过度模糊的匹配则可能改错位置。一个好的工具应把歧义反馈给模型，而不是静默挑一个近似位置。对于高影响修改，宁可让模型补充上下文，也不应把不确定性藏在执行器内部。

### 12.4 连续编辑与级联影响

如果一次操作包含多个替换，后一个旧文本可能出现在前一个新文本里，造成意外级联。社区专题描述了对这类情况的检查。它提醒我们，补丁不是互不相关的字符串集合，而是有顺序、有中间状态的操作序列。理解这种关系有助于避免模型把原文件的多个片段独立规划后，忽略第一步已经改变第二步的匹配环境。

但有级联检查也不等于多文件事务。一个文件修改成功、另一个文件失败时，系统可能处于部分完成状态。模型需要读取实际差异，决定继续修复还是报告范围，不能假定工具已经自动回滚全部操作。尤其在用户有未提交改动时，任何恢复都必须限定到本任务产生的变化，不能用粗暴重置来制造干净状态。

### 12.5 锚点的真正贡献

锚点替换把“我要改这里”变成可机械核对的陈述，是减少定位幻觉的一种有效结构。它不会代替名称解析、类型推断、测试或需求理解。它的价值恰好在于边界清晰：发现旧文本不存在时拒绝，发现位置不明确时要求澄清，接受后仍交给下一层验证。这种职责明确的局部检查，比一句无法执行的“请确保代码完全正确”更容易维护。

## 13. 新鲜度、mtime 与并发修改

[![本文整理：读取、外部修改、拒绝过时编辑与重新验证的时序](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis02-read-edit-freshness.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis02-read-edit-freshness.webp)

*来源：本文整理。内容指纹与验证合同用于说明更强的工程设计，不代表 Claude Code 全部采用此实现。*

**图解决的问题。** 模型看到的世界与它准备修改的世界可能不是同一个版本。**图中结构。** Agent 读取后，其他写入者改变文件，旧编辑请求应被拒绝或重新核对；随后验证需要针对新的实际内容。**支持的结论。** 正确观察具有时间条件，刷新状态是必要恢复动作。**不能证明的内容。** 一次新鲜度检查不能保证之后再无外部写入，也不能提供整个文件系统的事务隔离。

### 13.1 读过为什么还不够

在协作工作区里，用户可以在 IDE 修改文件，格式化器可以自动重写，构建进程可以生成产物，其他 Agent 也可能同时工作。读取记录若永久有效，就会把历史观察误用为当前依据。社区专题描述了比较修改时间与记录时间的路径，以发现读取之后发生的变化。这是把证据新鲜度落实到执行前检查的一种常见办法。

需要精确理解时间字段。不同实现可能记录读取时刻、当时的文件修改时间或其他状态标识。本文依据的是分析文档给出的流程，不把内部字段名称当作跨平台规范。关键关系是：运行系统必须判断当前对象是否仍与先前观察足够一致，而不是简单相信会话历史里曾经出现过文件内容。

### 13.2 时间戳是代理，不是内容本身

mtime 检查成本低，但它不是内容的完整身份。某些同步软件可能改变时间戳而不改变内容；文件系统分辨率、拷贝方式和外部工具也可能影响时间比较。社区分析特别提到 Windows 路径中的完整内容复核：在某些条件下，时间戳变化后还检查完整读取内容是否一致，以减少误报。这里不能把“某个平台的一条回退路径”写成所有平台都进行内容哈希校验。

反过来，仅比较内容也有范围问题。如果此前只读取片段，整文件变化可能发生在片段之外；片段内未变不意味着修改仍然安全。对局部替换而言，外部变化可能完全无关，也可能改变整个函数的语义前提。系统可以保守拒绝，也可以采用更复杂的冲突检测，但无论哪种选择，都需要让模型知道当前判断依据，而不是隐藏不确定性。

### 13.3 检查与使用之间仍有窗口

即使刚刚检查文件未变，另一个进程仍可能在检查之后、写入之前修改它。避免在同一进程内交错执行多次编辑，可以减少一类竞争，但不能约束外部进程。真正的跨进程保证通常需要文件锁、原子替换、版本条件或更高层事务协议，并且还要理解其平台语义。本文没有证据表明目标产品对所有写入入口提供了这样的完整保证。

因此，社区材料里“串行执行确保不会出现竞争条件”应收窄为“降低受该调度器控制的调用之间的交错风险”。同样，一次工具调用成功或失败的逻辑完整性，不等于崩溃一致性，更不等于多个文件一起提交。技术分析中最容易失真的地方，往往就是把一个局部性质写成全局绝对性质。

### 13.4 本任务自己的写入也会改变状态

编辑后需要更新读取缓存，否则下一次编辑可能把自己刚产生的修改误认成外部变化。社区专题提到了这一步。它说明新鲜度管理并不只是检测别人做了什么，还要让运行系统准确记录自己已经改变了什么。一个状态更新遗漏会造成过度拒绝，过度宽松又会漏掉冲突，两者都影响使用体验和可靠性。

这也是为什么结果证据不能只绑定 Git HEAD。多个未提交修改可以在同一个 HEAD 下连续发生，测试前后 HEAD 完全相同，却已经不是同一个待验证对象。更合适的合同应至少记录相关工作树内容、依赖锁文件和关键配置。是否需要整个树的指纹取决于任务范围，但不能假定提交标识涵盖所有运行状态。

### 13.5 面对冲突的合理行为

收到过时状态错误后，Agent 应重读、比较用户改动和自己的意图，再决定如何继续。它不应通过覆盖写入强行绕过冲突，也不应自动删除别人的改动以恢复原计划。如果外部变化与任务无关，可以保留并继续；如果影响接口或验收条件，应重新调整方案。新鲜度检查的目的不是阻碍工作，而是让决策再次基于真实状态。

工程上还应记录冲突频率。频繁发生的冲突可能说明任务划分不合理、多个工作者共享了过多写集合，或生成器在后台不断重写文件。继续提高模型推理能力未必解决这类问题，调整工作区隔离和写入职责反而更有效。可靠性分析必须愿意把一部分失败归因于系统协作方式，而不是全部归咎于语言模型。

## 14. Edit、Write、Notebook 与 Bash 不是同一个入口

[![仓库原图：编辑、写入与 Notebook 工具的整合](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo05-edit-tool-integration.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo05-edit-tool-integration.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/05-code-editing-strategy.md, 与工具系统的整合, MIT. 非官方历史实现分析图。*

**图解决的问题。** 模型面对不同文件操作时有多个工具选择，而不是单一写入按钮。**图中结构。** 普通文本修改、新文件写入和 Notebook 单元编辑分别进入对应工具，再与执行系统衔接。**支持的结论。** 专门工具可以表达更明确的操作语义。**不能证明的内容。** 不能从图中的文件工具推导所有 Shell、外部编辑器或 MCP 服务都执行相同前置检查。

### 14.1 创建与覆盖应分开

创建一个不存在的文件，通常不需要先读取该文件；覆盖已有文件则需要避免丢失现有内容。两种操作如果共用接口，执行器也应根据状态区分。社区文档明确把不存在文件的正常创建路径与已有文件读取要求分开。文章不应把这条规则简化为“所有写入都必须先读”，否则既不准确，也会把合理的新建操作描述为违规。

覆盖已有文件还可能扩大错误面。模型即使只想改一行，也可能在重新输出整个文件时遗漏注释、兼容代码、用户新增内容或细小格式。局部编辑因此通常更容易审计。但全文件写入并非天然错误：生成文件、模板替换和明确授权的重写都有合理用途。选择工具应依据任务与风险，而不是将某个工具绝对化。

### 14.2 Notebook 的对象不是普通行号

Notebook 同时包含单元、执行状态、输出和元数据。把它当作一大段 JSON 随意替换，很容易产生结构合法但语义混乱的结果。专门单元编辑接口可以缩小修改范围，保留对象身份。但它仍然不能证明单元执行顺序正确，也不能自动消除旧输出对读者的误导。保存成功与完整重新运行整个 notebook，是不同的交付状态。

这类区别可以推广到其他结构化对象。修改数据库字段、日历事件、设计稿或权限模型时，业务工具往往比任意文本写入更能表达约束。模型不必自己重建整份结构，执行器也更容易检查版本和合法关系。然而，结构化接口只能检查已编码的约束，仍需要验证业务意图是否正确。

### 14.3 Bash 的通用性与旁路风险

Shell 可以执行编辑器、脚本、重定向和外部程序，因此能力范围远大于专用文件工具。即使 Edit 有读取记录检查，也不能据此断言 Shell 写文件会走同一段逻辑。权限与沙箱可能限制 Shell 的访问，但它们解决的主要是可执行范围，不是自动复用每个文件工具的全部业务前置条件。

这不是鼓励绕过检查，恰恰相反，它说明系统设计不能只审计最漂亮的一条入口。如果某个安全或可靠性要求必须适用于所有写入，就需要在共同执行边界、工作区权限或外部验收层建立约束。仅在工具描述里要求“请优先使用 Edit”，不足以形成全局保证。实际采用时也应避免用更宽泛的工具逃避一个有意义的拒绝。

### 14.4 外部工具的承诺不能自动继承

通过 MCP 暴露的工具可能由不同服务实现，具有不同的事务、权限和错误语义。Claude Code 能把它们纳入统一调用形式，不代表它们的副作用都具有相同保证。某工具返回成功可能表示异步任务已创建，另一个则表示数据已持久化。模型需要遵循具体工具契约，而不是把所有 `tool_result` 都读成同一种完成事件。

因此，审阅 Agent 轨迹时，应同时看“调用了什么”和“通过哪个入口调用”。同样的目标动作，经不同入口可能留下不同日志、产生不同验证范围，也可能绕过不同检查。把这些差异写进工具能力矩阵，会比只统计工具名称数量更有工程价值。

## 15. 从修改落盘到程序正确

### 15.1 验证是一条逐步扩大的证据链

编辑工具返回成功，能支持“某次写入被执行器接受”的陈述。读取 diff，可以支持“文件确实发生了这些变化”。类型检查通过，可以支持“在当前类型配置下没有发现被检查的类型错误”。测试通过，可以支持“已执行的测试用例满足断言”。真实用户流程通过，才进一步支持“在这组输入与环境下目标行为成立”。每一步都有自己的范围，不能跳级。

这种分层不意味着必须在每次任务中从头到尾运行所有检查。关键在于修改风险。修改局部展示文案，差异检查和构建可能已经足够；修改公共解析器，需要更多输入边界；修改权限或交易逻辑，需要服务端集成与失败路径。验证计划应在实施前大致确定，并在发现新的影响范围时更新，否则容易在写完代码后只挑最容易通过的检查。

### 15.2 LSP 是反馈通道，不是完整验收

社区编辑专题提到编辑后向语言服务发送变化通知。这能帮助发现语法、类型或符号问题，但不能把通知本身当成诊断完成。异步通知可能尚未处理，语言服务可能没有启动，当前文件也可能没有纳入项目配置。即使诊断为空，也只说明该工具在当前条件下没有报告问题，不代表所有行为正确。

对于大型仓库，编辑器诊断和正式构建还可能使用不同配置。例如编辑器关注当前包，CI 编译整个工作区；本地使用增量缓存，CI 从干净环境开始；某些生成步骤只在正式脚本中执行。Agent 应优先遵循仓库实际命令，而不是凭语言或框架常识推测一个验证命令。这里再次回到先读取事实的原则。

### 15.3 测试为什么也会给出假安心

测试可以通过但没有验证到改动。常见情况包括测试过滤条件过窄、用例被跳过、路径配置排除了目标文件、只运行了旧构建产物，或者测试断言本身没有覆盖错误行为。一个退出码为零的命令，可能只是成功发现零个测试。可靠报告需要核对执行数量、关键用例、覆盖对象和最终状态，而不是只提取一个绿色词语。

测试也可能被实现者无意中削弱。为了让新代码通过而删除失败断言、扩大容忍范围或替换真实依赖为过度简化的模拟，都会让验证失去辨别力。模型不一定在故意欺骗，它可能把“让测试通过”误解为目标本身。因此，差异审查应同时关注生产代码和测试变化，确认测试仍然表达用户需要的性质。

### 15.4 真实场景验证的价值

有些问题只有重新运行原始失败场景才能验证。例如界面在手机宽度溢出，构建成功无法说明布局修复；异步取消仍然产生后台写入，单次函数返回无法说明副作用停止；权限问题只在某角色出现，管理员账号测试无法代表普通用户。原始复现条件应作为验证合同的一部分，而不是在实现过程中被遗忘。

实际场景验证仍有范围限制。一次成功交互不能证明所有设备、网络和并发条件都正确，性能结果也不能脱离硬件与数据规模。可靠报告应陈述“验证了哪些场景”，并保留尚未覆盖的边界。这样用户可以决定是否需要进一步验收，而不是被一个没有条件的“已经修好”误导。

### 15.5 验证失败后的诚实推进

如果完整测试因环境缺失无法运行，仍然可以做静态检查、局部测试或构建，但必须把替代证据与原目标分开。比如“类型检查通过，集成测试因数据库不可用未执行”是有用的交付状态；“全部验证通过”则不成立。缺少环境不是必须停止一切工作的理由，却是限制最终结论的理由。

本文尤其强调，失败、跳过、未运行和检查器错误不是同一个状态。失败说明某项断言没有满足；跳过说明流程有意不执行；未运行说明没有证据；检查器错误说明测量过程本身不可靠。把它们统一折叠成布尔值，会让模型和用户都难以作出正确后续决策。后文的完成合同将进一步把这些状态结构化。

## 16. 系统提示词：行为引导不是执行证明

### 16.1 提示词仍然重要

强调程序检查，并不意味着提示词没有价值。工具无法覆盖所有开放式判断，模型仍需要知道任务目标、沟通方式、探索策略和遇到不确定性时怎样行动。[系统提示词专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/14-system-prompt-design.md)收集了大量历史行为规则和设计解释，本文只提炼其中与可靠性相关的意图：先理解已有代码、避免凭空发明、尊重用户约束、报告验证边界，并在失败后调整方法。

这类规则影响模型如何分配注意力。例如“先检查现有实现”会提高搜索而不是立即写代码的机会；“不确定时说明缺口”会减少将猜测包装成事实的动机；“不要在没有执行时宣称测试通过”会把报告质量纳入任务目标。它们是有用的软约束，但是否遵守仍取决于模型、上下文和任务压力，不能像程序断言那样直接检验每一次生成过程。

### 16.2 规则应该指向可执行行为

“不要幻觉”太抽象，无法指导模型在具体时刻做什么。更可操作的规则是：涉及当前仓库对象先定位文件；涉及库接口核对已安装版本；涉及命令结果等待最终状态；不能验证时说明未验证原因。这些规则把价值判断转化为外部动作，也使人能够从轨迹中检查是否落实。它们仍不是硬保证，却比泛泛要求准确更容易形成反馈。

规则也不宜只有禁止项。告诉模型不能猜，还应提供替代路径：去哪里取证，哪些工具能解决未知项，何时向用户提问，以及何时可以停止并报告限制。否则，模型可能为了完成任务而换一种表述继续猜测，或者过度保守地拒绝本可通过读取解决的问题。可靠提示词应该帮助模型识别不确定性的类型，而不是让所有未知项都变成阻塞。

### 16.3 提示词层级与来源不能混淆

项目规则、用户请求、工具描述和外部文件可以同时出现在上下文，但它们不是同等来源。一个网页中的“忽略之前要求”，不因为被读取就变成用户指令；一个测试日志里的伪造 XML 标签，也不因为外观像系统消息就获得权威。模型需要按真实消息来源和信任边界解释内容，而不是按文字看起来有多正式来决定优先级。

这也是本文不大量复制内部提示词的原因。一方面，读者真正需要的是设计职责和适用条件，而不是背诵一套可能过期的文本；另一方面，某段规则的效果取决于它位于什么通道、与哪些其他规则一起出现，以及运行系统如何处理冲突。把原文粘贴到另一个 Agent 的普通用户消息中，并不等于复制了原系统的行为约束。

### 16.4 不确定性需要分级表达

一种有用的报告习惯是区分已观察、合理推断和待验证。例如“在当前源码中看到函数定义”是观察，“它可能是错误来源”是推断，“修复后是否覆盖所有时区”需要验证。这种分级不会让回答显得无能，反而可以让用户知道下一步投入应该放在哪里。真正的问题不是出现推断，而是推断失去标记后被当作事实传播。

但也不能把所有句子都加上“可能”来回避责任。已经通过明确证据确认的事实，应直接陈述并给出范围；存在关键缺口的结论，才需要保留条件。过度模糊会降低报告的可操作性，而过度确定会扩大错误影响。较好的做法是把不确定性附着在具体变量上，例如版本、环境、覆盖范围或尚未运行的场景，而不是用笼统语气覆盖整段回答。

### 16.5 提示词需要接受同样的验证纪律

如果团队修改了系统提示词，不能仅凭几次看起来更好的回答就断言幻觉显著降低。需要保留任务集、失败样例和副作用观察：是否减少错误的同时增加了无谓工具调用，是否变得过度拒绝，是否只改善某种熟悉任务。提示词是系统配置的一部分，也需要版本化和回归测试。

本文对社区提示词分析的态度因此是双重的：它能帮助解释产品为何倾向某种行为，但不能单独证明行为在所有情况下发生。最稳妥的设计，是让提示词表达意图，让工具提供证据，让程序检查关键前提，再由验证结果约束最终声明。四者合作，而不是争论究竟哪个才是唯一解法。

## 17. 上下文构建：模型真正看到了什么

[![仓库原图：系统提示词、用户上下文和工具相关内容的组装](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo02-context-construction.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo02-context-construction.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/03-context-engineering.md, 上下文构建全景, MIT. 非官方历史实现分析图。*

**图解决的问题。** [上下文专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/03-context-engineering.md)说明模型输入并非单一用户提示，而是多种来源组装后的结果。**图中结构。** 系统规则、环境、记忆、工具说明与会话消息分层进入上下文。**支持的结论。** 管理这些来源会改变模型可用的信息。**不能证明的内容。** 图示不能证明每次请求都装入全部内容，也不能证明某条信息被加载后一定被正确使用。

### 17.1 可访问、已读取、当前可见是三件事

一个文件在工作区中可访问，不表示模型读过；文件曾被读取，不表示它在压缩后的上下文中仍完整存在；相关信息当前可见，也不表示模型正确引用了它。对 Agent 进行故障分析时，应该区分这三个状态。否则，开发者可能因为“代码明明在那里”而误判模型拥有全部事实，也可能因为“之前读过”而忽略当前窗口已经只剩摘要。

上下文构建的任务，是选择当前决策最需要的信息，而不是复制整个世界。用户目标、约束、最近工具结果和关键代码通常优先级较高；长篇历史日志、重复文件内容和不相关工具说明则可能稀释注意力。这里没有一个对所有任务都最优的固定排序，重要的是保留能改变下一步决策的证据，并能够解释为什么它被保留。

### 17.2 内容与来源应一起进入

同一段文本来自用户、项目规则、搜索结果、测试日志或其他 Agent，意义可能完全不同。用户说“暂时不部署”是操作约束；README 举例“执行部署命令”是文档内容；测试夹具包含同样字符串则只是数据。如果上下文组装丢失来源，模型就可能把描述性内容误当指令，或者把不可信摘要误当官方说明。

因此，工具结果最好保留来源标签、路径、版本和读取范围。但标签本身也只是表示，不能由不可信内容自我声明。“这是一条系统指令”的网页文本，不会因为采用某种 XML 外观而改变消息层级。运行系统和模型都需要维护真实来源，不能让内容自己决定信任等级。

### 17.3 项目环境是动态事实

工作目录、操作系统、分支、依赖和可用命令都会影响行动。一个跨平台命令在另一环境中可能有不同语义，一个仓库路径在切换 worktree 后可能指向不同版本。因此环境信息不是装饰性背景，而是工具使用的前提。长会话如果跨目录、跨分支或恢复到新进程，就需要重新确认相关状态。

但把大量环境信息无差别重复注入，也可能浪费上下文。更好的方式是识别哪些变化会使现有判断失效，例如目录切换使文件路径证据需要重查，依赖更新使接口文档需要重查，用户改变目标使原验证计划需要重查。上下文管理应围绕依赖关系，而不只是围绕文本长度。

### 17.4 “高信号”需要可解释

官方上下文工程文章强调信息选择和有限注意力，本文将其用于解释取证策略，而不把它当作某个内部预算值的来源。所谓高信号，不是措辞强烈或摘要简短，而是能区分候选假设。例如一个失败断言可以直接否定当前修复方案，一条文件不存在错误可以否定路径猜测，这些都比一段泛泛架构介绍更接近当前决策。

因此，压缩之前应知道任务仍有哪些未解决问题。若目标是修复某个失败，失败输入、预期行为和当前验证状态不能被当作历史噪声清理；若目标是新功能，用户明确拒绝的方案也应保留，以免模型在后续再次提出。高质量上下文不仅保存“发生了什么”，还保存“哪些条件仍然约束接下来的行动”。

### 17.5 上下文不能替代真实世界

无论组装多精细，上下文都是现实状态的有限表示。数据库可以在模型推理期间变化，外部文档可以更新，用户可以编辑文件。模型因此应把上下文中的状态事实视为带时间的观察，而不是永久真理。能够按需返回工具重新确认，正是 Agent 与封闭式文本生成的关键差异，也是后续压缩恢复机制的基础。

## 18. 五级压缩：保留能力与遗失风险

[![仓库原图：工具结果预算、历史裁剪、微压缩、上下文折叠与自动压缩](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo03-compaction-pipeline.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo03-compaction-pipeline.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/03-context-engineering.md, 五级压缩流水线, MIT. 非官方历史实现分析图。*

**图解决的问题。** 长会话不断增加工具输出和历史消息，需要在有限窗口内继续工作。**图中结构。** 原图按工具结果预算、History Snip、Microcompact、Context Collapse、Autocompact 展示渐进处理。**支持的结论。** 压缩不是只有一次“总结前文”，不同处理层可保留不同形式的可恢复信息。**不能证明的内容。** 不能把图当成所有当前会话固定执行五步的保证，部分功能受开关、阈值和运行条件控制。

### 18.1 先审计“四级”和“五级”的差异

固定仓库 README 的概述仍出现“四级”表述，专题正文则列出五级，主循环流程也包含更细的处理节点。本文按专题图逐层解释，同时保留这个文档一致性问题。它提醒我们，架构总览可能落后于细节章节，不能只读首页就给出精确实现结论。类似地，`v2.1.6x` 与 `v2.1.88` 的版本口径也不能在引用时默默合并。

### 18.2 工具结果预算：从全文变成引用

第一层处理巨大的工具输出。社区分析描述了将部分大结果持久化、在上下文保留预览与路径的做法。它的优势是把大文本从持续上下文中移出，同时保留回查机会。这里必须区分原始结果确实被保存，与某工具在更早阶段已经截断：如果上游只返回一部分，后续持久化也无法凭空恢复缺失内容。

这种处理没有额外模型摘要调用，并不意味着没有计算、磁盘和时延成本。把“无需额外推断”写成“零成本”是不准确的。对可靠性而言，重要的是预览应明确说明不完整，模型不能仅凭开头几行就总结整个结果；需要完整证据时，应重新读取持久化内容或缩小原查询。

### 18.3 History Snip 与 Microcompact

历史裁剪试图移除某些冗余或可舍弃部分，微压缩则针对旧工具结果等内容做更轻量处理。它们可能比完整摘要便宜，但每次删除都在决定什么信息对后续不再必要。对于重复的目录列表，这种判断通常风险较低；对于只出现一次的失败条件、授权边界或用户纠正，风险就高得多。

社区材料还描述了不同缓存与时间条件下的路径。本文不把具体历史阈值当成当前可依赖的设置，也不根据某个开关名字推断所有用户已经启用。机制阅读的重点是识别被删除的对象和恢复办法：是只清理显示视图，还是从当前消息列表移除；完整内容是否另有记录；模型是否知道自己看到的是替代表示。

### 18.4 Context Collapse 与 Autocompact

上下文折叠在专题中被描述为投影式处理，保留原始消息而改变当前可见视图。完整自动压缩则可能用摘要替换当前历史表示。二者都节省窗口，但信息损失与恢复成本不同。原始消息仍存在，不代表模型每一步都能访问全部；摘要替换也不等于磁盘上的历史日志必然被物理删除。应该同时讨论会话表示和持久化层。

专题还列出压缩后恢复最近文件、技能、计划和工具增量通告的措施。这体现了一个重要思路：摘要之外，还需要恢复继续执行所依赖的结构化状态。本文不将“最近几个文件”之类历史预算写成永久协议，因为恢复数量和触发方式可能随版本与配置变化。真正可迁移的设计是，压缩必须考虑任务继续所需的前提，而不只是生成可读摘要。

### 18.5 压缩不是事实校验

摘要模型可以把错误结论写得更简洁，压缩器也可能保留一个未经验证的成功状态。上下文变短后，原来与它冲突的日志却消失了，于是错误反而更难被纠正。压缩成功只说明窗口得到控制，不说明内容变得更真实。因此，关键验证状态最好有可回查来源，不应只存在于一段自然语言总结中。

## 19. 压缩怎样重新引入幻觉

[![本文整理：失败证据在摘要中丢失，以及回到原始证据的恢复路径](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis03-evidence-loss-and-recovery.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis03-evidence-loss-and-recovery.webp)

*来源：本文构造的失败模式与恢复路径，不是记录到的 Claude Code 事故。*

**图解决的问题。** 为什么系统已经运行过工具，最后仍可能给出无依据的成功报告？**图中结构。** 原始失败结果经过压缩后丢失否定条件，模型据进展推断成功；恢复路径要求重读证据并检查是否对应当前工作树。**支持的结论。** 证据可恢复性与状态新鲜度必须同时考虑。**不能证明的内容。** 图中没有给出这种错误的发生概率，也没有证明某个压缩算法一定会产生它。

### 19.1 否定条件比进展摘要更容易被省略

工程会话中，正面进展往往更容易概括：增加了函数、修改了配置、完成了页面。失败条件却常带有具体环境与例外，例如某个测试只在夏令时切换时失败，某个请求只有普通用户角色不能通过，或者某个构建阶段尚未执行。如果摘要只保留“已经修复日期函数”，就可能把待验证的假设误写成完成事实。

这种风险不是压缩独有，人类交接也会出现同样问题。区别在于 Agent 可能在没有原始记忆的情况下继续工作，对摘要中的陈述赋予过高信任。设计上应优先保留未解决项、失败状态、用户约束和证据位置，而不是只保存行动列表。行动描述解释做过什么，状态描述决定还能声称什么。

### 19.2 推测被反复转述后会失去身份

第一轮说“问题可能来自缓存”，第二轮总结成“正在修复缓存问题”，第三轮记忆写成“这个项目的故障来自缓存”，一个假设就这样变成了事实。每一步看起来只是简化表达，却逐渐丢掉置信度与来源。多 Agent 汇报、长期记忆和自动摘要都可能放大这种现象。

防线不是要求每个句子都永久附带长注释，而是在关键状态上保留明确分类。候选原因、已验证原因、已实施修改、已通过检查应该是不同项目；不能因为时间过去或任务状态更新就自动升级。对于高风险判断，摘要应同时保留支持证据和仍然可能推翻结论的条件。

### 19.3 旧证据恢复后也可能已经无效

重读一个完整日志，可以恢复当时发生了什么，却不一定证明现在仍然如此。日志对应的代码、依赖、配置和输入可能已经变化。因此恢复流程需要两步：先确认原证据内容，再判断它是否适用于当前对象。只做第一步，可能把遗忘问题修成了过时事实问题。

这也是为何“路径仍存在”不是充分条件。日志文件可能被覆盖，文件名可能复用，某个输出目录可能包含前一次运行结果。更强的记录应有运行标识、内容指纹或不可变产物链接。对于轻量任务，可以采用简单的时间与差异核对；对于发布和数据迁移，则需要更严格的版本绑定。

### 19.4 信息损失不能总靠再次推理弥补

如果原始结果已经被截断且没有保存，模型再聪明也无法恢复不存在的信息。此时应该重新运行可重复的检查，或明确承认无法验证；不能让模型根据剩余片段补全日志。对于有副作用或不可重复的动作，更需要在首次执行时保存关键证据，否则后续可能没有安全的补采机会。

这种区分能指导成本投入。重复读取源码通常代价较低，而重新执行支付、删除或生产迁移不应作为普通证据恢复策略。系统应该根据动作可重复性决定记录强度，把不可逆或难重现操作的证据保存得更完整。上下文优化不能以丢失关键审计信息为代价。

### 19.5 面向继续工作的摘要

一份好的工程摘要应回答：当前目标是什么，已经改变了什么，哪些验证实际完成，哪些失败仍然存在，下一步需要读取什么，以及哪些行为没有授权。它不是对话的文学概括，而是继续决策所需的状态交接。将这种摘要与原始证据链接结合，可以在控制窗口大小的同时降低错误结论自我强化的机会。

本文并不声称这套摘要格式是 Claude Code 内置协议。它是从社区压缩机制和常见工程风险推导出的采用建议。价值在于可检验：读者可以拿任意一段交接摘要，检查是否把推测升级成事实、是否丢失失败和范围、是否能回到原始证据，而不是只凭摘要读起来顺不顺畅评价质量。

## 20. 证据恢复与新鲜度合同

### 20.1 给证据一个最小身份

为了避免将路径、记忆和结果混为一谈，本文提出一个解释性证据元组：

$$
e=(s,v,\ell,t,r,\Omega).
$$

其中 $s$ 是来源，$v$ 是版本或内容指纹，$\ell$ 是定位信息，$t$ 是观察时间，$r$ 是观察结果，$\Omega$ 是覆盖范围。这个表示不是官方 API，也不是要求所有工具都实现同一张表；它只是帮助读者检查一条证据是否缺少关键限定。不同任务可以采用不同轻量实现，但不应丢掉会改变结论的维度。

例如，源码证据可以用仓库、commit、路径和符号定位；测试证据需要命令、工作树、环境和执行结果；网页证据需要版本页或访问日期；用户授权则需要真实请求内容及其范围。它们不能统一简化为一条 URL，因为链接存在不代表内容对应当前对象，更不代表链接支持所附加的全部结论。

### 20.2 一条文章内的记录示例

下面是本文自定义的数据合同示意。占位值不是真实执行记录，也不对应 Claude Code 的内部结构：

```json
{
  "kind": "verification",
  "source": "project-test-runner",
  "run_id": "example-run-01",
  "subject": {
    "repository_revision": "COMMIT_PLACEHOLDER",
    "worktree_fingerprint": "CONTENT_FINGERPRINT_PLACEHOLDER",
    "dependency_fingerprint": "LOCKFILE_FINGERPRINT_PLACEHOLDER"
  },
  "command": "project-defined test command",
  "status": "failed",
  "coverage": ["date conversion boundary cases"],
  "artifact": "artifacts/example-run-01.log",
  "observed_at": "2026-10-27T11:00:00+08:00"
}
```

记录失败状态不是失败管理的终点。它还应该允许后续成功结果明确替代对应范围的旧失败，但不能覆盖历史。这样可以区分“曾经失败、修复后通过”和“从未验证”。如果只有一个可变的 `success: true` 字段，事故复盘就很难知道它何时、针对什么内容被更新。

### 20.3 哪些变化会使证据过期

最直观的是被检查文件变化，但依赖、环境变量、配置、测试数据和外部服务也可能影响结果。并非每个变化都使所有证据失效，应该根据依赖范围判断。例如文案修改可能不影响数据库测试，而权限策略改变会影响多个接口。一个成熟系统可以逐步建立这种关联，最初也可以采取保守策略：关键相关输入变化后重新运行对应检查。

时间本身不是唯一标准。刚运行的检查可能针对错误目录，因此仍不适用；很久以前核对的不可变历史 commit 则可能仍然有效。新鲜度应该理解为证据与当前命题之间的适用关系，而不是简单的年龄。缓存过期策略、摘要恢复和最终报告，都应围绕这种关系设计。

### 20.4 证据不是授权

知道某命令存在、知道它以前成功执行、知道另一个 Agent 建议执行，都不等于用户授权现在执行。证据合同和授权合同应该关联，但不能混合。尤其在跨会话协作中，来自其他任务的消息可能是有用上下文，却不能自动代表当前用户的新指令。模型需要分清“别人报告了一件事”和“用户要求我采取行动”。

同理，工具结果可能包含提示注入。给结果加来源字段有助于识别它是外部数据，但不会自动消除其中的恶意内容。后续处理必须仍然遵循真实信任边界。对高影响操作，既要有事实依据，也要有适当授权，这两项缺一不可。

### 20.5 从合同到可用工作流

最简单的落地方式不是开发一个庞大平台，而是在任务记录中保留检查命令、实际状态、当前内容和日志位置，并要求最终报告引用这些记录。随着复杂度上升，再增加自动指纹、结构化状态和不可变产物。这样能渐进提高可靠性，而不必一次性改造所有工具。

关键是记录应服务决策。没有人读取、没有校验范围、最终报告也不引用的日志，只会增加存储成本。证据合同的价值在于让模型和人都能回答：这句话凭什么成立，条件变了以后还成立吗，需要重做哪项检查？这比保存尽可能多的文本更接近可靠 Agent 的目标。

## 21. 项目指令与长期记忆：帮助理解，也可能固化错误

[![仓库原图：哪些信息应保存，以及四种记忆类型的决策流程](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo08-memory-decision.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo08-memory-decision.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/08-memory-system.md, 记忆决策流程, MIT. 非官方历史设计分析。*

**图解决的问题。** [记忆专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/08-memory-system.md)讨论哪些跨会话信息值得保存，哪些应该重新从代码和文档读取。**图中结构。** 作者按可重新获取性、是否重复和信息类型进行分流。**支持的结论。** 长期记忆不应成为所有临时状态的堆积场。**不能证明的内容。** 图里的分类与排除策略不能被当成所有当前版本、所有记忆产品的统一协议。

### 21.1 项目规则不是事实缓存的替代品

项目指令适合保存团队约定、验证命令、所有权边界和无法从代码轻易推出的背景。自动记忆适合保留有长期价值的偏好、纠正和外部参考。但某个文件当前包含什么、某次构建是否成功、某个分支是否已合并，应该优先从现有环境重新确认。把易变状态长期缓存，会让模型在后续会话中携带过时的确定性。

[官方记忆文档](https://code.claude.com/docs/en/memory)明确将项目说明和自动记忆视为上下文，而不是强制配置。当前文档还讨论 `AGENTS.md` 支持及其加载条件，不能将历史材料中主要围绕 `CLAUDE.md` 的描述写成当前唯一入口。本文不修改读者的配置；这里只强调来源与加载方式必须按实际版本核对。

### 21.2 为什么需要保留原因与适用范围

“不要使用模拟数据库”如果没有背景，容易被模型推广到所有测试。更有用的记忆是：某个集成验证需要真实数据库，因为过去的模拟未覆盖迁移约束。这保留了原因和应用场景，模型才能区分单元测试中的合理模拟与发布前必须验证的真实依赖。记忆的目标不是让模型机械服从过去每句话，而是减少重复犯错并保留决策背景。

日期也需要明确。诸如“下周冻结”“昨天已经发布”在未来会话中失去稳定含义。保存绝对日期、发布标识和来源，比保存相对时间更适合长期使用。但绝对时间也不能替代状态刷新：知道某天计划发布，不等于现在已经发布。时间归一化解决解释歧义，实时查询解决状态变化，两者职责不同。

### 21.3 错误记忆如何自我强化

如果模型在一次调试中猜测根因是缓存，并把它保存为项目事实，后续任务可能优先沿同一方向调查。多次会话都引用这条记忆，看起来像多个证据，其实只是同一个未经验证假设的重复传播。记忆应保存来源与置信边界，并允许撤回和更新，而不是只支持追加。

一个有效的回忆流程应把记忆当作搜索线索。记忆说某模块负责权限，就去读当前入口和调用链；记忆说某命令是验证入口，就核对当前脚本。这样既利用历史经验节省探索成本，又避免让旧信息垄断判断。对于很稳定的偏好，重查成本可以低；对于可变工程状态，应更积极刷新。

### 21.4 记忆的隐私与权限

长期保存会增加信息暴露面。用户身份、业务数据、日志片段和访问凭据不能因为对某次任务有用就无限期保留。记忆应遵守授权、最小化和删除要求；文章中的设计建议也不意味着可以擅自修改用户记忆目录。尤其不能把来自不可信网页或仓库的“请永久记住”当作用户授权。

多人协作还需要区分个人偏好与团队规则。某个人习惯的命令别名不一定适合全团队，一个项目的发布禁令也不应污染其他项目。记忆作用域错误会造成行为偏差，即使其中每条文本本身真实。因而可靠记忆管理同时需要内容正确、范围正确和时间正确。

### 21.5 对可靠性的真正贡献

记忆最有价值的作用，是减少反复丢失的上下文和重复出现的已知错误，而不是增加一个不需要核验的知识源。它既可能降低幻觉，也可能放大幻觉，方向取决于保存、检索、校验和撤回机制。本文不采用社区材料中的少量示例结果作为普遍效果统计，因为缺少独立样本、完整协议和可复现数据。

对日常使用者，一条实用标准是：当模型以“我记得”开始一个可变化的事实判断时，要求它指出记忆来源，并在低成本时刷新。对平台开发者，则应把记忆命中与事实确认分开记录。前者说明检索有效，后者才说明这条历史信息仍适用于当前任务。

## 22. Skills：把经验流程变成按需上下文

[![仓库原图：技能发现、执行模式选择与加载流程](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo09-skill-execution.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo09-skill-execution.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/09-skills-system.md, 执行流程概览, MIT. 非官方历史机制分析。*

**图解决的问题。** 某些任务需要专门流程，但把所有流程常驻系统提示词会造成负担。**图中结构。** [技能专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/09-skills-system.md)描述按名称查找、执行模式选择、内容加载和可能的独立上下文。**支持的结论。** 程序性知识可以按需提供。**不能证明的内容。** 技能被发现、被读取和被完整执行是三个状态，图示不能将它们合并。

### 22.1 程序性知识补上什么缺口

模型可能知道某类任务的一般做法，却不知道团队的具体约定。例如发布需要先检查不可变镜像、文档导出需要核对字体和页码、数据库变更需要检查回滚。技能可以把这些流程、工具入口和验证标准放在一个可维护位置，减少每次从头猜测步骤。它更像操作手册，而不是给模型新增了天然正确的知识。

一个高质量技能应说明适用条件、输入要求、步骤顺序、失败处理和完成标准。只有命令列表而没有条件，会诱导模型在不合适环境中机械执行；只有原则而没有验证，又容易回到“认真检查一下”的抽象要求。将这些信息组织成按需阅读的材料，可以降低常驻上下文负担，同时提高复杂任务的过程一致性。

### 22.2 发现错误与执行错误要分开

技能未被选中，可能是描述不清、任务匹配失败或目录不可用；技能被选中但执行失败，则可能是步骤过期、工具不兼容或模型没有遵循。评价技能效果时应区分这两类问题。只统计调用次数，不能证明它改善了任务质量；只看最终结果，也难以知道失败发生在发现还是执行阶段。

渐进加载还带来一个预算问题：技能简介过短可能不利于匹配，正文过长可能挤掉实际代码证据。适合常驻的是能力描述和触发条件，细节可以分层读取。这里应避免将完整手册全部注入后再称为“按需加载”，因为文件被模块化组织不等于运行时上下文成本已经降低。

### 22.3 技能也会过期

工具参数、CLI 命令、服务地址和版本要求都可能改变。一份曾经正确的技能，在新版本上可能产生虚构参数或错误步骤。因此技能应具有来源、适用版本和更新记录；遇到接口拒绝时，模型应回到当前文档，而不是因为技能写着某命令就不断尝试。权威感不能替代时效性。

对于社区技能，还要考虑信任边界。技能内容可能包含 Shell 命令、网络请求或敏感信息处理指令，不能因为文件放在约定目录就自动视为可信。读取技能是获取操作建议，真正执行仍需要符合用户目标和授权。一个被恶意修改的技能，可以把程序性知识入口变成提示注入入口。

### 22.4 流程遵循如何被验证

如果技能要求运行测试，最终应有测试执行证据；如果要求检查某个发布标识，就应保留该标识和查询结果。不能用“已按技能执行”替代实际记录。对于关键流程，可以让程序 Hook 或 CI 执行必要检查；对于开放式判断，则保留人工审阅。技能负责告诉模型应该做什么，执行系统负责让关键步骤不轻易遗漏。

还应允许有理由的偏离。某个步骤不适用于当前环境时，模型可以说明原因并采用经授权的替代验证，而不必为了形式完整运行危险或无意义命令。流程可靠性不是逐字照抄，而是保证每个关键目标得到对应证据。对偏离进行记录，比把例外隐藏在“全部完成”的总结中更利于维护。

### 22.5 与普通提示词的关系

技能没有改变语言指令本身的性质。它仍然主要通过模型理解和选择影响行为，只是增加了可复用组织与按需分发。它可以显著改善团队知识传递，却不能承担所有强制规则。对必须始终执行的校验，应使用可测试的程序路径；对需要灵活判断的任务经验，技能则是更适合的表达方式。

## 23. Plan Mode：减少需求假设，而不是提前证明实现

[![仓库原图：进入规划、探索、用户审批和返回执行的时序](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo10-plan-sequence.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo10-plan-sequence.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/10-plan-mode.md, 完整 Plan 模式流程, MIT. 非官方历史实现分析图。*

**图解决的问题。** 一个复杂请求可能存在多种解释，直接修改会把未确认的选择变成事实。**图中结构。** [Plan 专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/10-plan-mode.md)将探索、方案、提问、计划记录和审批与执行分开。**支持的结论。** 规划可以在变更前暴露关键假设。**不能证明的内容。** 原图中的具体阶段和子 Agent 使用是历史分析，不代表每个任务都必须按同一模板运行，也不代表批准计划就证明代码正确。

### 23.1 哪些问题应该先探索

文件位置、现有模式、测试命令和依赖版本，通常可以从仓库发现，不应一开始就推给用户。真正需要用户决定的是偏好、产品意图、风险接受度和无法从环境推导的约束。把可发现事实与偏好问题分开，可以减少无效提问，也避免模型把个人猜测伪装成用户需求。

例如，用户要求“优化搜索”，可能是减少延迟、改善相关性、增加过滤功能或降低成本。仓库可以告诉我们现有实现，但不能替用户选择目标。一个可靠计划应将这种高影响歧义提前提出，同时给出可评估选项。相反，询问“测试脚本在哪里”而不先看配置，只是在转移探索工作。

### 23.2 计划的价值在决策，而不是篇幅

好的计划应明确目标、范围、现有事实、关键变更、验收和风险。它不必穷尽每一个代码行，却应该让实施者知道遇到主要分支时怎么选择。过度冗长的计划可能把真正需要确认的决策埋起来；过度简短则会把高影响选择留到实现过程中由模型擅自决定。规划质量取决于决策是否完整，而不是列表数量。

对减少幻觉而言，计划还有一个好处：它把“我认为用户想要什么”变成用户可见文本。用户可以纠正模型，而不是等到大量代码写完才发现方向错了。这种纠正针对需求层面，不应被算成模型事实检索能力提升。不同可靠性机制解决不同错误，评价时仍需分开。

### 23.3 审批的范围必须保留

批准实施某个功能，不等于批准推送、部署、删除数据、购买服务或修改其他项目配置。计划中如果明确不包含这些行为，执行阶段应保留限制。长会话压缩或多 Agent 交接尤其容易丢掉范围声明，因此计划文件和摘要都应保留关键边界，而不是只留下任务名称。

审批也不意味着所有假设永远成立。实现中发现依赖不兼容、接口行为不同或已有用户改动时，应调整局部方案，重大偏离则重新确认。把“用户已经批准”当作忽略新证据的理由，会让规划从可靠性工具变成僵化执行的借口。计划是当前决策依据，不是冻结现实世界的命令。

### 23.4 规划阶段同样要避免虚构

只读并不意味着没有风险。模型可能在计划里发明不存在的模块、声称某功能已经支持，或者低估迁移成本。因为尚未执行，这些错误不一定立即暴露，却会影响用户批准。因此计划中的关键事实也应有来源，无法确认的能力应标为待核验，而不是用确定语气填满方案。

一个可实施计划还应明确如何验证关键假设。例如采用某库接口前核对版本，修改共享模型后检查所有调用者，处理异步状态时重跑原失败场景。这使计划不仅描述要做什么，也说明怎样知道它做对了。这样的验证设计比最后附一句“运行测试”更有实际价值。

### 23.5 何时不必使用重规划

并不是每个简单修改都需要长篇方案。对于意图明确、范围很小且易于验证的任务，直接读取相关文件并执行更有效。规划的收益随着歧义、影响范围和不可逆性增加，而不是随着模型想展示多少过程增加。可靠系统应该让流程强度适配任务，而不是让用户为所有操作承担同样的沟通成本。

## 24. 子 Agent：上下文隔离与相关错误

[![仓库原图：父子 ToolUseContext 中克隆、替换与共享的状态](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo07-subagent-context.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo07-subagent-context.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/07-multi-agent.md, 上下文隔离深度解析, MIT. 非官方历史状态结构图。*

**图解决的问题。** 子 Agent 并不是简单复制一个聊天窗口，父子上下文之间可能有不同共享策略。**图中结构。** 原图显示读取缓存、取消控制、应用状态、任务状态和追踪信息分别采用克隆、包装、新建或共享。**支持的结论。** 隔离需要逐项定义，不能只用“独立 Agent”一词概括。**不能证明的内容。** 它不能证明外部文件、数据库和服务也被隔离，不能证明子任务取消一定撤销已经发生的副作用。

### 24.1 为什么分工可能帮助可靠性

[多 Agent 专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/07-multi-agent.md)和[官方子 Agent 文档](https://code.claude.com/docs/en/sub-agents)都提供了理解独立上下文与工具范围的材料。把探索、实现和验证分开，可以减少单个窗口中的无关信息，也可以让验证者更专注于反例而不是解释自己的设计。这是合理的工作流动机，但不是自动成立的准确率保证。

分工最有价值的情况，是任务可以被清晰拆成相对独立的问题。例如一个 Agent 检查接口兼容，另一个检查测试覆盖，主 Agent 负责整合。若所有工作者都收到同一个带有错误结论的摘要，又只被要求确认它，就可能得到多个相同答案而没有新增证据。并行数量增加，不等于独立信息增加。

### 24.2 独立上下文不等于独立错误

即使上下文完全分开，多个 Agent 可能共享模型、训练偏差、工具限制和文档来源。它们容易在同一类模糊接口、相似名称或缺失信息上犯相同错误。因此，不能把“多个 Agent 都同意”直接解释为统计独立的重复验证。没有独立性证据，就不应使用简单的错误概率相乘来制造强置信度。

更有效的做法是让验证者接触原始对象，并提出不同类型的检查。一个通过阅读代码寻找反例，一个运行行为测试，一个核对用户验收条件，比三个 Agent 都阅读同一份总结更可能发现不同问题。这里的多样性来自证据和方法，而不仅是角色名称或提示词中的人格设定。

### 24.3 克隆状态能解决什么

原图中读取状态采用克隆，可以避免子任务的某些操作直接改写父任务的观察记录。新建取消控制也有助于管理生命周期。但克隆的是某一时刻的内部状态，不是对外部世界拍了不可变快照。子任务执行期间文件可能变化，父任务拿到结果时也可能已经处于另一版本。

任务状态在图中又包含共享路径，这意味着某些协调信息仍然跨上下文传播。共享有助于协作，也要求区分“谁报告了什么”和“真实执行了什么”。把任务标记更新当作测试证据，会再次把管理层状态误认为结果层状态。隔离与共享需要按对象分别讨论，而不是给整个系统贴一个统一标签。

### 24.4 交付物比叙述更重要

子 Agent 的结果应包含可检查对象：差异、文件位置、命令状态、日志或明确未验证项。主 Agent 在整合时应检查这些证据是否对应当前工作树，而不是直接复制最终总结。如果子任务只提供观点，则应保留观点身份；如果提供运行结果，则应核对环境和范围。分工可以减少工作量，但不能完全外包最终责任。

同样，不应要求验证者只找正面证据。一个有用的验证任务应明确要寻找哪些失败模式，并允许得出“无法验证”。当任务设计把成功报告当作唯一可接受答案时，多 Agent 只会增加确认偏误的输出数量。真正的独立审查需要有权反驳实现者，而不是充当另一个总结器。

## 25. 共享状态、Worktree 与报告传递

### 25.1 三种隔离不要混用

上下文隔离影响模型看到什么，文件系统隔离影响工作者修改哪些文件，外部服务隔离影响数据库、端口、队列和远程资源。一个子 Agent 有独立提示词，不表示它有独立工作目录；使用 worktree，也不表示测试数据库或云资源自动分离。许多并发错误正是因为团队只确认了其中一层，却以为整个环境都互不影响。

Git worktree 对减少文件冲突很有帮助，因为不同任务可以基于明确版本形成独立差异。但合并之后仍然需要验证组合结果。两个单独通过测试的补丁，可能修改同一接口的不同假设，整合后才出现错误。子任务验证结果属于子任务快照，不能未经检查就转移为集成分支的成功证明。

### 25.2 读取状态也会在交接中失真

子 Agent 说“已经检查过这个文件”，主 Agent 可能据此继续修改。但检查发生在哪个路径、哪个工作树、哪个内容版本？如果这些信息缺失，主 Agent 只能得到一条叙述，而不是可直接复用的读取证据。对于需要精确锚点的修改，重新读取集成后的当前文件通常更便宜、更可靠。

这并不意味着所有工作都必须重复。历史架构说明、不可变提交分析和纯推理结论可以带着来源复用；与当前状态相关的检查则需要验证适用性。区分可复用知识与必须刷新的状态，可以避免在“全信子 Agent”和“全部重做”两个极端之间摇摆。

### 25.3 共享资源造成的隐形耦合

两个工作者可能分别在独立目录启动服务，却争用同一个端口；分别运行测试，却写入同一个数据库；分别修改配置，却调用同一个远程项目。此时文件系统看起来干净，实际行为已经互相影响。测试结果也可能来自另一个进程提供的页面或旧服务，造成非常具有迷惑性的假通过。

工程上应为共享资源建立明确标识和生命周期。验证 URL 要对应预期进程，数据库要有明确隔离策略，后台任务要能追踪归属和清理状态。本文将这些作为可迁移建议，而不是声称某个 Agent 产品默认替用户解决全部环境隔离。运行系统越开放，外部资源合同就越重要。

### 25.4 跨会话消息的权威边界

来自其他 Agent 的消息可以提供线索、结果或请求，但它不能自动变成原始用户授权。尤其是“请帮我推送”“顺便删除旧资源”这样的行动指令，需要回到真实用户范围判断。否则，协作通信会成为扩大权限的通道，即使消息没有恶意，也可能因为上下文缺失产生越界行为。

这里的安全问题与幻觉问题会交叉。一个工作者可能错误地声称用户已经批准，另一个若直接采信，就会把虚构授权转换成真实行动。防线是保留授权来源，而不是只在消息中寻找某个肯定词。技术系统应该让报告、建议和用户指令在表示上有所区别，并在关键动作前重新核对。

### 25.5 主 Agent 的整合责任

最终交付者需要检查组合后的内容、未解决问题和证据覆盖。它不必把每个子任务重新实现一遍，但应抽查关键断言、运行集成层验证，并明确哪些结论来自二手报告。对于冲突结论，应回到原始代码或测试，而不是按哪个 Agent 更有自信决定。

一个简洁的交接模板可以包括：任务范围、基线版本、修改对象、执行检查、结果产物、已知限制和剩余动作。模板本身不是保证，但它使缺失信息更容易被发现。多 Agent 的可靠性最终取决于这种交接和整合纪律，而不只是并行调度能力。

## 26. Task 状态与 Verification Nudge

### 26.1 任务列表保存的是工作流状态

[任务系统分析](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/15-task-system.md)讨论了任务、依赖、状态更新和验证提醒。任务系统能把一个大目标拆成可追踪步骤，使“还剩什么”不完全依赖模型记住整段对话。这对长任务有实际帮助：读取、实现、验证、文档更新可以作为不同工作项存在，未完成项也比较容易在交接时被发现。

但是任务状态首先是一种管理声明。把某项设为完成，可能只是模型调用了状态更新工具，并不意味着系统已经运行测试、读取测试报告或检查产物。即使更新操作被可靠持久化，它证明的也是“完成标记写入成功”，不是“被标记的工作正确”。这与数据库成功保存一条审核意见、却不保证审核意见真实，是同一种层次差异。

因此，任务系统应当区分工作完成与验收完成。某个实现任务结束之后，可以产生一个等待验证的交付物，而不是立即让所有下游任务继承成功。尤其当验证步骤依赖环境、权限或外部数据时，“暂时无法运行”应当成为可见状态，不能为了清空任务列表而被合并到完成状态中。

### 26.2 历史提醒并非默认全量验证

固定社区快照中的 Verification Nudge 有明确触发条件：主线程、所有任务完成、任务总数至少为三，而且任务标题中没有匹配到 `verif` 的内容。该路径还同时受 `VERIFICATION_AGENT` 与 `tengu_hive_evidence` 两个开关控制。这是**社区快照分析**中的实验性路径，不是本文独立确认所有 Claude Code 用户都会执行的默认机制。

这些条件本身也暴露了提醒的能力边界。按标题字符串判断是否已有验证任务，只能是一种启发式。如果任务叫“verification”，却从未执行检查，名字不会变成证据；如果真正进行了验证，但标题使用中文，也不能据此推断该历史判断会准确识别。提醒有助于把遗漏拉回注意力，却没有理解任意项目验收要求的完备能力。

不要因为变量名包含 agent，就推断它必然启动独立审查模型，更不要把提醒文本当成已经产生验证结果。本文能确认的是分析资料描述了某条提醒路径及其条件。实际产品是否开启、具体如何调度、用户环境是否满足条件，都不能由这个名字单独决定。

### 26.3 依赖图解决顺序，不解决真实性

任务依赖能够表达“先构建，再测试”“先迁移数据，再切换读取”，但状态传播是否可靠仍然取决于每个节点的完成判据。若上游把失败误标为成功，依赖图会非常有效地把错误送入下游。把流程结构画得更复杂，并不能替代对节点输出的校验。

一个更稳健的任务节点应当记录交付物与验收引用。例如实现任务指向具体差异，测试任务指向当前内容快照上的运行报告，发布任务指向被部署的不可变产物。这样，依赖不只是任务编号之间的关系，也能沿着证据追溯。本文把这种设计作为工程建议，不将它写成历史 Task 系统已经完整提供的保证。

### 26.4 完成判据需要允许未验证

对于静态阅读文章，“已解释代码路径”可以作为合法成果；对于线上故障修复，“本地构建通过”却不能替代原场景恢复。完成标准取决于用户目标，不能统一简化成执行了某条命令。若任务只授权分析，未运行系统并不构成失败；若任务要求修复运行问题，未验证行为就必须明确保留。

这也是为什么任务计数不适合作为可靠性指标。十个全部打勾的小任务可能比一个认真运行的端到端测试提供更少信息。好的任务系统帮助团队组织证据，而不是鼓励模型生产漂亮的完成率。最终报告应当把做了什么、观察到什么、仍不知道什么分别表达。

## 27. Hooks：程序触发不等于检查充分

[![仓库原图：Hook 执行引擎与输入输出路径](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo06-hook-engine.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-repo06-hook-engine.webp)

*Source: Windy3f3f3f3f/how-claude-code-works, commit f4d6505ed9162a0ee6be089190f74c419ecacb19, docs/06-hooks-extensibility.md, Hook 执行引擎, MIT. 图示为社区历史分析，不是当前完整事件规范。*

**图解决的问题。** 检查不应只靠模型临时想起来执行。**图中结构。** 原图将事件输入、匹配、不同处理器、结果解析及控制反馈连接起来。**支持的结论。** 宿主程序可以在特定生命周期位置触发外部检查。**不能证明的内容。** 触发不代表脚本成功运行，脚本成功运行不代表覆盖所有风险，处理器返回意见也不代表该事件允许阻止动作。

### 27.1 把检查从建议变成执行点

[Hooks 专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/06-hooks-extensibility.md)提供了理解执行引擎的历史材料。模型软指令与 Hook 的关键区别，在于后者可以由程序在事件发生时调用，而不必等模型主动提出检查。这降低了“知道规则但忘记执行”的一类风险，但没有自动解决规则怎么写、检查什么和失败如何处理的问题。

例如在修改后运行格式检查，可以减少漏掉基本格式问题的机会；在执行敏感命令前检查参数，可以拦截已知危险模式。两者的结果性质不同：格式检查关注产物约束，命令检查关注行动范围。它们都不直接回答需求是否被正确实现。把各种 Hook 统称为“反幻觉系统”，反而会模糊每种检查的真实职责。

### 27.2 前置、后置与结束事件的位置不同

前置检查发生在动作之前，因此有机会阻止某些副作用。后置检查面对的则是已经执行的动作，只能检查、反馈或启动补救流程，不能假装外部世界从未改变。结束事件更接近工作流收尾，可以提示遗漏，但它看到的通常也是一组记录和模型声明，而不是完整业务状态。

这种位置差异意味着同一段验证逻辑放在不同事件中，约束强度并不相同。一个检查到生产写入才报警的后置脚本，不等价于写入前阻止操作；一个要求补跑测试的结束提醒，也不等价于发布平台拒绝没有有效报告的产物。读者应先问检查发生在哪个副作用边界，再讨论它是否足够严格。

### 27.3 确定性处理器与模型判定处理器

脚本可以检查文件是否存在、结果格式是否正确、报告是否覆盖当前内容，这类条件相对容易形成确定性判定。但“实现是否满足复杂自然语言需求”往往需要更丰富的上下文，甚至再次借助模型。后者可以提高审查覆盖，却会重新引入理解错误、提示注入和过度自信等问题。

因此，“程序保证调用了一个模型检查”与“程序保证结论正确”是不同命题。前者约束调度，后者需要额外证据。对于可机器判定的条件，优先使用明确检查；对于必须判断的条件，让模型提供理由和证据，并保留人工或独立行为测试的出口。不要用一个自然语言评分替代所有结构化验收。

### 27.4 Hook 自己也是需要验证的软件

检查脚本可能读错路径、解析错误日志、只检查最后一个命令、误把缓存报告当作新结果。它还可能因为环境变量、工作目录或运行时版本不同而失效。越是准备把它放在强约束位置，越需要为脚本本身设计正反例，而不是只证明“成功情况会显示绿色”。

最基本的验收至少应覆盖脚本缺失、输入不合法、检查超时、明确不通过和成功通过。对于修改参数或返回上下文的 Hook，还应检查返回格式与当前事件的协议是否一致。本文没有安装这些 Hook；这里是在说明建立验证门槛需要完成的工程工作，而非展示已经运行的客户端配置。

### 27.5 不要让检查脚本成为新权限通道

Hook 常运行在与用户相近的本地权限环境中。它可能访问源码、日志和网络，因此不能把它视为天然安全的小附件。尤其不应直接把模型输出、外部网页文字或工具日志拼成 shell 命令执行。验证证据应该被当作数据解析，而不是被重新解释成指令。

审计与最小权限同样适用于 Hook。只读检查不应获得发布凭据，质量门槛不应暗中上传整份项目，失败报告不应泄漏环境变量。把可靠性措施放进程序，并不免除对这个程序本身的安全和隐私审查。

## 28. 验证门槛的失败路径

### 28.1 当前规范与历史快照必须分开

截至本文查阅日期，官方 Hooks 文档规定：`command` 和 `http` 可用 `onFailure: "block"`，要求 `v2.1.295+`；该选项不作用于 `Stop`、`SubagentStop`、`TaskCompleted`、`TeammateIdle` 或后台异步命令 Hook。Stop 不处理用户中断，API 错误走无决策控制的 StopFailure；连续续跑还存在八次上限，工具调用会重置计数。这些是**当前文档规则**，不倒写为社区旧快照行为。[官方 Hooks 参考](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)、[Stop](https://code.claude.com/docs/en/hooks#stop)。

这里最重要的推论不是记住某个退出码，而是承认“检查器未能作出判断”与“检查通过”不同。一个系统可以为了交互可用性选择在检查器失效时继续，但采用者不能再把该检查当成绝对门槛。可用性取舍本身未必错误，错误的是对外宣称了比实际协议更强的保证。

### 28.2 文章中的前置检查示例

下面是**配置示意，本文未创建该文件，也未运行脚本**。它针对当前文档所述的前置事件，不是通用停止门槛。脚本名由本文定义，检查规则需要项目自行实现；不能仅复制配置就声称获得完整安全审查。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/check-command.js"],
            "timeout": 15,
            "onFailure": "block"
          }
        ]
      }
    ]
  }
}
```

这个示例强调检查器故障要有明确处理策略，而不是建议用简单字符串黑名单判断所有 shell 行为。命令语法、子进程、重定向和间接脚本可能使表面匹配失真。真正的前置策略需要限定允许的动作集合，并将权限隔离与参数检查结合。它主要约束行动，不会替用户判断代码是否满足业务需求。

### 28.3 停止检查适合反馈，不应冒充发布锁

结束时检查缺失验证项，可以让模型补充工作，但它仍然处于会话控制层。会话被打断、进程异常退出、检查器未启动，或者检查无法形成有效结论时，都不能假定所有交付途径被封住。要阻止未验证产物进入生产，约束应放在真实发布入口，例如由独立系统校验产物和报告关联，而不是依赖模型一定继续聊天。

即使停止检查成功返回“请继续”，重复执行也可能没有意义。环境凭据缺失、测试数据不可访问或依赖服务关闭，不会因为再提示几次自动修复。此时应报告阻塞原因和未验证范围，并避免把无限续跑当作认真负责。重试预算是资源控制，不是正确性证明；耗尽预算后需要明确状态，而不是把失败改名为完成。

### 28.4 检查器需要拒绝哪些假证据

以下伪代码表达本文建议的报告验收逻辑，不是 Claude Code 内部函数，也不是可直接运行的完整 Hook。`current_snapshot` 必须包含实际相关内容，而不只是 Git HEAD；报告解析应使用结构化格式，不执行报告中的任何字符串。

```text
verify_report(report, current_snapshot, required_checks):
    if report is missing or cannot be parsed:
        return ERROR("没有可读取的验证报告")
    if report.snapshot != current_snapshot:
        return ERROR("报告属于另一内容快照")
    for check in required_checks:
        result = report.find(check)
        if result is missing:
            return NOT_RUN(check)
        if result.status != PASSED:
            return result.status
        if result.requires_tests and result.test_count == 0:
            return ERROR("没有实际执行测试")
    return PASSED_WITH_SCOPE(required_checks)
```

这里的核心是先确定报告存在且适用，再看结果是否成功。只在日志中寻找“passed”会受到历史输出、子命令输出、颜色转义甚至恶意文本影响。结构化报告同样可能伪造，因此还要限定谁能生成、在哪里存放、如何关联执行。对于高风险门槛，应由独立执行器生成结果，避免被被审查任务随意改写。

### 28.5 故障策略必须可观测

如果检查器选择继续，应把检查未完成显示出来；如果选择阻断，应说明是政策拒绝、测试失败，还是检查器自身故障。这三种情况需要不同恢复动作。把它们统一显示为“检查失败”会诱导模型盲目修改业务代码，实际问题可能只是脚本路径写错。

良好的失败反馈还应给出下一步可验证动作，例如重新确认运行时、修复报告格式或在正确工作树执行检查。它不应要求模型绕过门槛来证明自己可以继续。一个门槛只有在失败路径同样可理解、可恢复时，才有机会长期被团队保留，而不是最终成为被关闭的噪声来源。

## 29. 防止虚假完成的证据合同

[![本文整理：从工作树快照到最终完成声明的证据链](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis04-completion-evidence.webp)](/images/blog/claude-code-hallucination-reduction-design/claude-code-analysis04-completion-evidence.webp)

*本文整理，基于本报告对执行、验证与声明边界的分析。不是 Claude Code 官方架构，也不是已部署门槛。*

**图解决的问题。** 最终回答为什么不能只依据模型的任务状态。**图中结构。** 工作树、检查运行、结果产物、覆盖范围和最终声明分开记录。**支持的结论。** 完成声明可以被追溯到具体观察。**不能证明的内容。** 合同本身不会自动生成测试，也不能使不充分的测试突然覆盖全部需求。

### 29.1 至少保留五种验证状态

| 状态 | 准确含义 | 可以怎么报告 | 不能怎么报告 |
| --- | --- | --- | --- |
| `passed` | 指定检查实际完成，判据通过 | 当前范围内检查通过 | 整个系统必然正确 |
| `failed` | 检查完成并发现不满足判据 | 测试发现失败，附范围 | 只是环境波动，无需证据 |
| `skipped` | 明确决定不执行，并记录原因 | 因约束跳过某项 | 与通过合并展示 |
| `not_run` | 尚未开始或没有执行证据 | 尚未运行该检查 | 已经验证，只是没日志 |
| `error` | 检查过程无法给出有效判定 | 环境或执行器出错 | 将检查器退出当业务失败或通过 |

状态名称并不神奇，重要的是团队不能只存一个布尔值。当所有非失败情况都被当成成功时，跳过、未运行和执行错误会悄悄进入绿色统计。对 Agent 而言，这尤其危险，因为模型容易根据“没有看到失败”推断“已经成功”，而中间可能根本没有执行。

### 29.2 HEAD 不是工作树指纹

一个仓库可以在 HEAD 不变的情况下修改多个文件、增加未跟踪代码或改变生成配置。因此，把测试结果只绑定提交哈希，无法证明它覆盖当前未提交状态。对于正在编辑的 Agent，验证时点与最终输出之间可能还有修改，旧结果必须重新判断适用性。

内容指纹也应有明确范围。如果只哈希已跟踪源码，测试实际依赖的未跟踪配置、构建脚本、锁文件或环境可能被漏掉。反过来，把全部本地文件都纳入又可能包含秘密和无关缓存。可行方案是定义影响执行的输入集合，并记录环境、工具版本和外部服务标识；不要将一个模糊哈希描述成完整世界快照。

### 29.3 检查通过仍需要覆盖说明

单元测试、类型检查、页面访问和用户流程测试验证不同性质。类型检查可能排除一类接口错误，却看不到错误业务规则；页面返回成功状态码，也可能只是渲染了空壳；模拟服务上的集成测试，不代表生产数据和权限路径一定正确。最终声明必须随证据范围缩放。

一个有用的报告不是罗列所有绿色命令，而是把检查与目标对应起来。例如“原报错用例已重跑”“改动涉及的两个入口均已覆盖”“实际外部服务未访问”。这种表达让用户能判断剩余风险。没有必要为了显得完整而宣布未执行的端到端验证，也不必把范围明确的局部验证贬低成毫无价值。

### 29.4 声明应当晚于最后一次相关修改

测试通过后再改一行代码，可能使测试结果失效。是否必须全部重跑，取决于修改影响范围；但至少应重新评估，而不是沿用先前的完成措辞。格式化、生成文件变化和依赖锁更新也可能影响实际构建，不能仅凭“看起来小”就视为不影响验证。

同样，重新部署、切换分支或更换配置之后，旧环境的结果不能自动转移。证据合同需要把时间顺序暴露出来：观察对象是什么，检查何时运行，之后发生过什么变化。这样可以发现“测试的是旧内容，报告的是新内容”的断裂，而不是只看某处是否有一次成功记录。

### 29.5 交付模板应简洁而不失真

本文建议的收尾结构是：变更摘要、实际验证、未验证项、必要风险或回滚信息。无需把所有日志粘贴到回答中，但应保留可定位证据。没有运行测试时，直接写明比用“逻辑上应该正常”代替更可靠；只能静态分析时，也应明确这就是本次工作范围。

完成声明的目标不是降低模型自信，而是让自信有可检查的根据。一个可靠 Agent 可以在证据充分时明确报告成功，也可以在证据不足时准确收缩结论。持续使用模糊措辞并不是诚实的唯一形式，准确区分已知与未知才是。

## 30. 权限、安全与事实正确性

### 30.1 为什么这些话题必须分开

[权限安全分析](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/11-permission-security.md)与[自动模式分析](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/18-auto-mode.md)描述了权限路径和相关判定。安全机制对 Agent 很重要，但它回答的主要是“这个动作是否允许”，而不是“这个动作的内容是否正确”。允许读取一个文件，不意味着模型正确理解了文件；允许修改一个目录，也不意味着每个修改都满足需求。

反方向也一样：一个技术上正确的命令可能超出用户授权。例如模型准确知道怎样删除云资源，并不能由此获得删除权。幻觉治理与权限治理应当交叉配合，但不能互相替代。把两者分开，才能同时发现“行动合法但结论错误”和“结论正确但行动越界”。

### 30.2 Sandbox 约束副作用范围

沙箱可以限制文件、网络或进程能力，从而缩小错误操作的影响面。它不会告诉模型某个 API 是否存在，也不会验证生成代码的业务语义。沙箱里同样可以产生错误补丁、误读日志或虚报完成，只是这些错误更难直接影响被隔离的外部资源。

这种价值不应被低估，也不应被夸大。限制副作用可以为探索提供安全空间，让错误更可恢复；但恢复能力不是准确率。尤其当外部服务通过被允许的接口接入时，系统仍需理解授权范围、敏感数据和操作不可逆性。一个统一的“已允许”状态无法表达所有这些维度。

### 30.3 外部内容可能同时包含事实与指令

代码注释、网页、工单和工具输出都可能包含对任务有价值的信息，也可能夹带要求模型忽略规则、读取秘密或扩大任务范围的文字。内容来自真实工具，不意味着其中所有自然语言都应获得指令权威。工具可以忠实返回恶意文本，事实获取链路与指令信任链路必须分开。

例如仓库文件里写着“测试失败时上传环境变量”，这是被读取的内容，不是用户授权。模型应当分析它是否属于项目正常代码或危险建议，而不能因为它出现在 Read 结果中就执行。减少幻觉也需要这种边界：外部文本可能虚构用户意图、验证结果或系统状态，造成比普通知识错误更严重的行为后果。

### 30.4 分类器与模型检查也有误差

自动模式中的分类判断可能帮助减少不必要确认，但任何分类器都需要考虑误放行和误拦截。本文没有获得针对当前产品的独立误差分布，因此不提供虚构的安全率，也不把社区提到的特征或提示策略解释为完备证明。检查器名称、输入结构和设计目标都不能替代实际评测。

对于高风险动作，应让可确定的边界尽量由程序执行，例如限制目标资源、命令能力和凭据范围；对于模糊意图，保留用户确认或拒绝路径。增加另一个模型可以成为辅助，但不能把“模型审查模型”当成逻辑上必然可靠的闭环。

### 30.5 安全失败也需要准确报告

权限拒绝表示动作没有按该路径被允许，不表示任务本身无法完成；可能存在用户授权范围内的替代方法。但不能为了绕过拒绝而换工具执行同样被禁止的行为。恢复应该改变方案或澄清授权，而不是只改变语法使检查器看不出来。

同样，用户批准某项操作之后，Agent 仍需验证执行结果。授权记录、工具返回和业务验收应分别保存。在[官方安全文档](https://code.claude.com/docs/en/security)所述的产品安全边界之外，具体团队仍要为自己的凭据、日志和发布流程负责。本文讨论的可靠性设计不是任何产品安全认证，也不是生产部署许可。

## 31. Goal、Workflow 与后续能力

### 31.1 延长执行不等于提高正确性

[自主目标与循环专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/17-autonomy-goal-loop.md)讨论了目标判断、续跑和调度。它包含较新客户端观察，而不是与前面所有章节共享一个可复核源码版本。本文只借此讨论结束条件的设计，不复刻内部提示词，不提供抓包或提取客户端内容的操作指南，也没有在本机运行这些功能。

一个持续运行机制可以减少模型过早停止，但如果目标模糊、反馈错误或验证缺失，它也可以让模型更长时间沿错误方向工作。可靠性不随执行轮数单调增加。新增轮次有价值的前提，是它带来新的观察、修正或验证，而不是不断把先前结论改写得更肯定。

因此，目标条件应该尽可能连接可观察结果。比如“让页面更好”很难被可靠判定；“在指定视口没有横向溢出，关键按钮可完成指定流程，并保留测试证据”更接近可验收合同。即便如此，仍需要说明哪些由程序检查，哪些需要人工判断，不能把自然语言条件自动视为机器可判定命题。

### 31.2 模型裁判的证据输入决定上限

如果结束裁判只看到执行者的一段总结，它可能被自信措辞误导。若能访问明确产物、最新检查状态和未完成项，判断基础会更扎实。但裁判自身仍可能误读结果，尤其在成功条件涉及复杂语义时。将裁判与执行者分开，可以减少某些直接偏误，却不能制造独立真实世界。

这里还需要区分“目前没有达到”“本次环境无法达到”和“目标在逻辑上不可能”。模型可能因为工具失败几次就过早放弃，也可能因为不愿承认限制而无限重试。可靠的状态机应保留原因和已尝试路径，让用户看到究竟是能力、资源、权限还是目标定义的问题，而不是只输出一个成功或失败标签。

### 31.3 Workflow 把哪些事情交给脚本

[动态工作流分析](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/19-dynamic-workflows.md)讨论了脚本编排、并发、结构化返回和预算。其证据包括工具描述、字符串与少量黑盒探针，涉及 `2.1.201/202`。这只能支持被观察路径的分析，不能被本文提升为完整服务端实现说明，也不能据此保证当前所有用户都有同一能力。

从工程角度看，将固定依赖、并发限制和结果合并交给脚本，可以减少主模型反复记住调度细节的负担。脚本能确定某个分支是否返回、某个字段是否存在，却不能仅因字段是布尔值就知道答案正确。结构化返回解决表示和传递问题，语义验证仍需明确判据。

例如子任务返回 `{"verified": true}`，若没有报告引用和内容指纹，仍然只是被 JSON 包装的声明。更好的结构应包含检查名称、状态、对象、时间和证据定位，并允许未知和执行错误。可解析性是可靠性的必要辅助，不是充分条件。

### 31.4 编排需要定义失败如何传播

并行任务中一个分支失败，后续是全部停止、部分继续，还是只重跑失败分支，应由任务语义决定。对于互不依赖的文档分析，可以保留已完成结果；对于必须一致更新的共享接口，则可能需要整体验证。不能把“尽可能完成更多任务”作为所有场景的唯一优化目标。

预算耗尽也应被显式表示。它说明资源限制到达，不说明目标已完成。子任务超时、返回空值或被取消时，聚合器必须保留这种缺口，不能在生成总结时把缺失结果补成听起来合理的内容。否则，确定性调度只是把不确定性送到了最后一个自然语言步骤。

### 31.5 后续观察不回填历史实现

[团队协作专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/20-agent-teams.md)自己就区分了旧快照材料与较新客户端观察。报告沿用这种分层，不把后来出现的共享产物、隐式团队或跨会话规则视为早期全部存在。对于字符串中可见但没有完整运行证据的能力，只讨论可能的接口含义，不描述成默认已部署功能。

阅读快速演进的 Agent 产品，应当把时间当成架构的一部分。某个旧缺陷可能已修复，某个实验路径可能已撤回，某段提示也可能被新的程序检查替代。保留版本不是形式主义，而是防止读者把历史机制用于错误的当前决策。

## 32. 可观测性与审计：日志怎样成为证据

### 32.1 四类记录不是同一种东西

[可观测性专题](https://github.com/Windy3f3f3f3f/how-claude-code-works/blob/f4d6505ed9162a0ee6be089190f74c419ecacb19/docs/16-observability.md)涉及指标、事件、追踪与会话记录。指标适合观察总体趋势，事件描述离散行为，追踪呈现调用关系，会话记录保存交互材料。它们可以互补，但不能假定任意一种记录单独就足以重建整个任务。

一次工具失败计数上升，可以提醒团队调查，却不能告诉审查者某份文件究竟被怎样修改。某条模型消息声称测试成功，也不能替代命令进程的退出状态。可靠审计需要为不同问题选择对应证据，而不是把所有内容都叫“日志”，然后认为只要有日志文件就能证明工作正确。

### 32.2 关联字段需要逐条验证

社区分析提到请求、事件序列和消息父子关系等字段。它们有助于关联，但字段出现在哪些记录里、是否始终存在、并发时如何排序，都不能靠命名推断。例如事件序列更接近记录顺序，不必然等于实际发生时间；会话父子关系也不一定能直接映射到每个外部进程生命周期。

工程上应建立明确关联模型：哪个用户请求触发了哪个工具调用，工具修改了哪些对象，哪次检查验证了哪个快照，最终声明引用了哪些结果。字段缺失时应保留断点，而不是用相近时间强行拼接成确定因果。尤其异步任务可能晚到、重试或跨会话恢复，简单时间排序很容易产生误配。

### 32.3 记录调用与记录结果要分开

“已调度测试”与“测试进程已启动”不同，“进程结束”与“报告成功生成”不同，“报告生成”与“满足验收条件”仍然不同。每个状态都可能在故障中停住。如果日志只记录开始事件，最终报告就不能从开始记录推导成功；如果只记录最终摘要，也难以区分中间是否跳过关键步骤。

对于长期任务，应特别记录取消和超时的副作用边界。取消模型等待，不一定取消已经启动的外部进程；工具超时返回，也不一定意味着远程操作没有完成。恢复前需要查询实际状态，避免重复执行不可幂等动作。本文把这点作为一般系统设计要求，不声称当前 Claude Code 的每个工具都有统一事务保证。

### 32.4 证据保留与隐私之间存在取舍

原始工具结果可能包含源码、个人信息、访问令牌或业务数据。为了审计保留全部内容，并不总是合适。可采用脱敏摘要、受控原始存储、内容指纹与最小必要字段组合，但要记录脱敏和截断发生在哪一步。否则，未来审查者可能把删减后的视图误认为完整原始输出。

权限也应随证据敏感度分层。项目成员能看到测试状态，不意味着都应该看到生产日志中的用户数据；模型能使用某个检索结果，也不意味着该结果应被发送到所有子 Agent。可观测性的目的在于帮助定位与验证，不是无限扩大数据流通范围。本文实施只读取公开分析材料，没有读取任何私人 Claude 会话。

### 32.5 监控要防止把活动量当质量

工具调用数、Token 数和任务完成数可以衡量成本或活动，但不能直接衡量事实可靠性。一个任务调用更多工具，可能是认真取证，也可能是在错误路径反复尝试。真正有用的可靠性监控还应观察未验证声明、过时报告复用、错误恢复、检查跳过和实际验收失败。

这些指标需要有可审计定义。例如“完成后回归失败”应明确回归场景与时间窗口，“无证据声明”应明确需要哪类证据。没有定义就统计，会让仪表盘呈现精确数字，却无法回答系统是否真的减少幻觉。量化本身不会消除概念混淆。

### 32.6 可回放不等于可重现

会话记录可以帮助理解模型当时看到什么，但重新播放请求未必得到相同输出。模型版本、采样、工具环境、文件和外部服务都可能变化。对于不可变源码分析，固定提交能保存对象；对于实际运行结果，还需要保存环境和输入。回放与复现是相关但不同的能力。

因此，本文没有用“存在 transcript”推出“全部行为可精确复现”。更合理的表述是：日志可以为调查提供线索和部分证据，完整重现需要更多条件。对于缺失条件，应该写明，而不是利用一段看似详细的追踪掩盖不可重现性。

## 33. 案例一：名字合理，但 API 不存在

### 33.1 构造一个可辨认的错误

本章是**本文构造的教学轨迹**，不是实际 Claude Code 会话，也不是对某个真实 SDK 的缺陷报告。设一个项目使用虚构的 `@example/catalog-client`，本地类型声明只提供下面的接口。包名、版本和方法均为说明问题而构造，读者不应把它们当成可安装依赖。

```ts
// Illustrative local contract, not a real package API.
interface CatalogClient {
  search(input: {
    query: string;
    limit: number;
  }): Promise<Array<{ id: string; title: string }>>;
}
```

用户要求增加搜索能力，模型却写了 `client.semanticSearch({ text, topK: 10 })`。这个调用听起来符合许多现代检索产品的命名习惯，却没有来自目标版本的证据。错误产生于把模式记忆当成接口事实，而不是产生于 TypeScript 语法本身。

### 33.2 第一层恢复：确认实际依赖对象

取证首先应确定项目真正解析到哪个依赖版本。清单中的版本范围、锁文件中的解析结果、工作空间链接和本地封装可能不同。只看包名就打开最新文档，容易把新版本接口套到旧项目；只看一个搜索结果，也可能忽略项目自定义适配器。

在这个构造案例中，Agent 应读取依赖与调用入口，搜索现有 `CatalogClient` 用法，再检查解析到的声明或实现。若项目提供封装，应先理解封装合同，而不是跳过它直接调用底层 SDK。这里的目标不是机械执行固定命令，而是确定正在讨论的接口对象和版本。

### 33.3 第二层恢复：把文档变成有限证据

对于真实库，官方对应版本文档可以补充参数语义、返回值和错误行为。但文档也可能滚动更新，示例可能省略默认配置。应把文档陈述与本地类型、源码或测试相互核对，遇到不一致时保留差异，而不是自动相信更新时间更新的一方适用于当前安装。

在本例中，已知声明只支持 `search`，因此不能直接宣称支持语义搜索。用户想要的能力可能需要另一个服务、模型或索引。可靠回答应说明现有接口能做什么，缺少什么，然后在授权范围内决定是否扩展。把需求中出现的“语义”二字改成一个方法名，并没有实现该能力。

### 33.4 第三层恢复：类型与行为分别验证

把调用改成 `client.search({ query: text, limit: 10 })`，可以使形状符合本地接口，但仍需验证实际行为。返回空数组可能是数据问题，错误排序可能是服务语义问题，超时可能需要调用方处理。类型检查只证明一部分静态合同，不会自动证明搜索结果相关或用户交互正确。

若代码中使用 `any`、动态代理或无类型外部响应，类型检查甚至可能无法发现虚构方法。这时需要更明确的适配层测试或受控运行检查。不能因为编译器没有报错，就说最初的 API 事实已经被确认。工具反馈的强度取决于工具实际检查了什么。

### 33.5 最终报告应该怎样写

一个准确报告可以说明：使用项目实际接口完成调用适配，类型检查覆盖了参数与返回值使用，行为测试验证了指定输入和异常路径；若没有访问真实服务，则保留真实数据质量和外部连通性未验证。它不必重复全部调查过程，但应让成功结论与实际证据一致。

不准确的报告则可能写成“已集成语义搜索，全部验证通过”，即使只消除了编译错误。这个案例说明，减少幻觉不是把错误函数名改对就结束，还要检查功能名称、行为承诺和验证范围是否继续夸大。

### 33.6 机制如何分工

搜索和读取帮助发现真实合同，版本核对防止引用漂移，Schema 约束工具调用本身，类型检查捕获部分使用错误，行为测试验证特定效果，最终证据合同约束报告。没有一个环节单独覆盖全部问题。把它们串起来，才能从“听起来像 API”逐步走向“被目标环境支持的行为”。

也应保留失败可能：错误类型声明、模拟测试与真实服务差异、搜索漏掉动态生成代码，都可能使调查不完整。可靠系统不是承诺每次必然找到真相，而是让每个结论附带清晰依据，并在新证据出现时可以被修正。

## 34. 案例二：过时文件与错误锚点

### 34.1 四类失败不能混在一起

本章同样是构造案例。设文件中有两个相似的重试配置，一个用于后台任务，一个用于交互请求。模型要修改交互请求，却只记住了“把重试次数改成三”。未读取、锚点不唯一、读取后发生外部修改，以及准确定位后写错语义，是四种不同失败，不能统一归因于编辑工具不可靠。

未读取时，历史读取前置条件可能阻止某条编辑路径。锚点不唯一时，替换工具可以要求补充上下文。读取已经过时时，需要重新确认当前内容。若定位唯一但把后台逻辑误当成交互逻辑，工具可能完全成功，这时只能依靠语义审查和行为验证发现问题。

### 34.2 多匹配是信息不足，不是工具刁难

假设旧字符串只有 `retryCount: 1`，它在文件中出现两次。拒绝替换是在避免让工具擅自决定哪个位置正确。合适的恢复是读取周围结构，使用包含调用域和属性名称的更完整锚点，而不是立刻打开全量替换。`replace_all` 改变的是操作语义，不是消除歧义的免费方法。

若用户确实要求统一修改所有位置，仍应确认所有匹配的业务含义一致。两个文本相同的配置可能具有不同延迟预算。工具能数出匹配次数，却不知道哪个预算来自产品约束。精准定位与正确意图需要共同成立，不能用其中一个替代另一个。

### 34.3 读取之后的外部修改

考虑一个时序：Agent 在时刻甲读取文件；用户在时刻乙增加超时保护；Agent 在时刻丙提交基于甲的替换。若只依赖旧上下文，新增逻辑可能被覆盖。新鲜度检查的作用，是让模型意识到自己的观察与当前文件可能不一致，然后重新读取和整合。

但是重新读取也不构成跨进程锁。读完之后仍可能发生新的写入，因此不能从某次检查成功推出完全不存在竞争窗口。对于共享文件的高风险更新，可能需要外部协调、内容条件写入或事务机制。本文不将历史 Edit 工具描述成具备所有这些保证。

### 34.4 正确恢复是与新内容共存

发现文件变化之后，Agent 应理解变化是否与任务相关。若用户新增了超时保护，不能为了让旧补丁容易应用而把它删除。应在当前内容上重新形成最小修改，并保留用户意图。只有新旧需求真正冲突、无法合理合并时，才需要请求进一步澄清。

这里的可靠性不只是防止写错字节，也是防止模型把他人的变更当作障碍随手清理。一个编辑工具拒绝了过时操作，后续恢复若采用整文件覆盖，仍然可能破坏保护效果。前置检查需要与谨慎的恢复策略配合，才能减少真实损失。

### 34.5 唯一锚点也可能完成错误需求

设 Agent 找到了交互请求的唯一配置，却把重试次数从一改成十，而用户目标是降低尾延迟。编辑可以成功，格式检查可以通过，甚至原有测试也可能通过。错误不在定位，而在对目标与约束的理解。此时需要检查重试策略与超时预算的关系，以及原失败场景是否改善。

这正是为什么“修改工具没有报错”不能写成“修复完成”。工具确认的是某种文本变换，它没有获得用户体验、服务负载和业务约束的完整判据。验证应针对需求提出的行为，而不是仅针对修改动作本身。

### 34.6 一个更完整的验收顺序

先确认目标文件与调用域，再读取当前内容；形成锚点后检查差异，确认没有覆盖无关变化；运行与目标行为相关的检查，最后核对验证后是否还有相关修改。这是本文建议的顺序，不是声称产品内部自动执行了每一步。

若任何一步无法完成，报告就应收缩到实际范围。例如“文本修改完成，尚未验证尾延迟”比“性能问题已解决”准确。对于非常小的变更，这一顺序可以很简短；对于并发修改和生产路径，则需要更完整记录。流程强度应随风险变化，而不是以步骤数量评判专业性。

## 35. 案例三：压缩后的失败遗忘

### 35.1 一条错误结论如何被洗成事实

设一次构造任务中，集成测试因为认证失败没有进入业务断言。模型随后做了局部修改，长会话触发摘要。摘要只保存“已处理认证问题，接下来整理报告”，却遗漏“尚未重跑集成测试”。恢复后的模型可能把处理动作理解为问题已经验证解决，最终宣布通过。

这里不一定存在蓄意欺骗。错误来自状态在压缩中被简化：执行了修复，被合并成修复有效；没有重试结果，被自然语言连续性补成成功。若错误摘要再被写入长期记忆或转发给子 Agent，多个后续上下文都可能继承同一个无依据结论。

### 35.2 证据损失发生在什么位置

需要区分三种情况。第一，原始日志仍在磁盘或持久化工具结果中，只是没有进入当前窗口。第二，工具返回时已截断，关键行从未被保存。第三，日志存在但对应的是旧环境，不能直接作为当前证据。三者的恢复成本不同，不能统一要求“去读一下日志”就认为解决了。

如果只是窗口遗漏，找到持久化结果可以恢复当时事实；如果上游已经丢失，可能必须重跑；如果环境变化，则需要重新验证适用性。压缩机制应该尽量保留证据定位和状态，而不是只保留一个结果形容词。对失败尤其如此，因为失败往往决定下一步应该做什么。

### 35.3 恢复时先审计状态，不先相信摘要

恢复后的 Agent 应先确认哪些断言来自摘要，哪些有独立结果。对于“认证已解决”，应寻找实际成功请求、正确身份和预期业务响应，而不是只看到配置修改。对于“集成测试通过”，应找到完整测试运行与覆盖范围。找不到时，应把状态降为未验证，而不是继续引用旧说法。

这种降级不是否定过去的所有工作。代码修改仍然可以保留，调查线索仍然有价值，只是验证结论不能凭空继承。工程系统应允许部分知识复用与部分状态重检同时存在，否则模型容易在全盘相信和全部重做之间选择不合适的极端。

### 35.4 记忆需要保存失败条件

如果把记忆写成“该项目需要某环境变量”，却没有说明它来自哪次失败、是否仍适用于当前部署，未来可能误导其他任务。更有用的记录是保留来源、适用环境和未验证边界。对临时故障、短期 workaround 和已淘汰接口，应避免写成永久项目规则。

这也说明自动记忆的维护不能只追求提取更多内容。错误规则比缺失规则更危险，因为它提供了看似熟悉的方向。团队应能够修正、过期或撤销记忆，并在高风险动作前回到当前事实。长期保存提升了可用性，也延长了错误可能影响系统的时间。

### 35.5 子 Agent 不应重复放大同一摘要

若验证者只收到“认证已经修复，请确认代码风格”，它可能根本不会检查认证路径。主 Agent 最后引用“独立审查通过”，就把一个有限风格检查升级成业务验证。问题不在子 Agent 没有完成任务，而在任务输入和最终解释都发生了范围扩张。

更好的审查请求应该包含原失败、当前假设、实际修改和明确未验证项，并要求验证者寻找反例。报告也应注明它检查了什么。独立性首先是证据与问题定义的独立，而不是启动了另一个对话进程。

### 35.6 阻断级联的最小措施

在压缩摘要中单列未完成验证，保留原始结果指针；恢复后先核对这些指针与当前内容；记忆只保存可复用知识，不把临时状态当成永久事实；子任务交接必须说明验证范围。最后，用新的实际结果更新状态，而不是在旧摘要上继续追加自信解释。

这些措施都不能保证摘要永远无误，但它们把错误从难以察觉的语言流变成可检查的状态断裂。本文认为，这比单纯增加一句“压缩时不要遗漏重要信息”更接近可以迁移到工程系统的设计。

## 36. 案例四：没有运行，却宣布通过

### 36.1 最容易被忽略的失败不是红色输出

这个构造案例从一句常见结尾开始：“测试全部通过。”审计时却发现模型只写出了准备运行的命令，没有实际工具调用。另一种情况是命令启动了，但进程仍在运行；还有一种是检查器退出成功，却没有发现任何测试文件。三者都不等于测试通过，但在过度压缩的叙述中很容易被归为同一成功状态。

可靠 Agent 应把意图、启动、完成和判定分开。计划运行只是未来动作，工具调用记录证明发起，进程结果证明执行状态，测试报告才说明覆盖与断言。缺少其中任何一环，都应收缩结论。尤其不能把回复中的代码块当作已执行记录，也不能从没有报错文本推断命令已经完成。

### 36.2 六种常见的假通过

| 构造情形 | 实际可确认的内容 | 应报告状态 | 下一步 |
| --- | --- | --- | --- |
| 只有命令文本，没有调用 | 有执行计划 | `not_run` | 在授权范围内实际运行 |
| 进程启动后等待超时 | 有未完成执行 | `error` 或继续等待 | 查询进程状态，避免重复启动 |
| 测试发现数量为零 | 检查器运行了 | 不接受为覆盖通过 | 核对路径、筛选器和配置 |
| 报告来自旧工作树 | 历史快照曾被验证 | 当前 `not_run` | 对当前内容重新检查 |
| 只跑局部用例 | 局部范围有结果 | 有范围的 `passed` | 明确未覆盖入口 |
| 测试入口被改为跳过 | 执行合同已改变 | 需审计后判定 | 比较测试与构建配置差异 |

表格中的状态是本文建议的报告分类，不是某个工具固定返回格式。它强调“没有发现失败”和“有足够通过证据”之间的差距。对于零测试，有些项目确实允许特定检查不含测试，但这必须来自明确合同，不能由 Agent 为了获得绿色结果临时决定。

### 36.3 超时不是失败，也不是成功

测试超时可能源于死锁、外部服务等待、资源不足或正常耗时超出观察窗口。若工具只停止等待，后台进程可能仍在执行。此时立即再次启动测试，可能导致竞争和污染，进一步让结果难以解释。应先识别执行器状态和副作用，再决定等待、终止或重试。

最终回答也应区分“测试断言失败”与“未能完成测试”。前者提供了功能不满足的证据，后者只说明当前没有有效判定。两者都不能报告通过，但恢复方向不同。把基础设施错误误诊为业务错误，可能诱导模型修改原本正确的代码。

### 36.4 测试了错误对象的危险

另一个隐蔽情况是访问了旧开发服务器。新代码已经写入，浏览器却连接到另一个目录启动的进程，页面看起来正常。返回成功状态码、截图和点击结果都是真实的，但它们证明的是旧服务。这不是伪造工具输出，而是把真实证据关联到了错误对象。

因此，验证 URL、进程、构建产物和内容版本之间需要建立联系。对于静态页面，可以核对实际渲染标题与资源；对于服务，可以核对可识别版本和启动目录。检查不一定复杂，但不能只认端口可访问。真实工具结果仍然可能被错误解释，这正是证据关联层的职责。

### 36.5 测试配置本身也可能被削弱

当 Agent 同时有权修改实现和测试，它可能无意中把严格断言改宽、跳过失败用例，或者改变脚本让测试不再运行。新的绿色结果就不一定代表功能改善。审查应同时看实现差异与验证差异，确认测试变化是修正错误预期，还是掩盖真实回归。

这不意味着测试永远不能改。需求变化时，测试必须演进；原测试也可能有错误。关键在于变化需要理由和独立证据，不能仅以“这样就通过了”为理由。对于重要验收，保留被实现者不能随意更改的外部测试或人工复核，是比不断强化完成提示更直接的措施。

### 36.6 一个诚实且有用的最终声明

合适的模板可以是：“已修改指定入口；当前工作树上的单元测试通过，执行了若干用例；集成环境不可用，因此外部服务路径未验证。”这里不填造测试数量，实际报告必须来自真实运行。若原失败场景已重跑，应单独说明，而不是让用户猜测它是否包含在一组笼统测试中。

诚实报告不需要夸张免责声明，也不应该把所有结果写得含糊。它需要准确指出证据能支持的边界。用户因此可以决定是否继续验收、提供环境或接受局部成果。减少虚假完成的最终目的，是改善决策，而不是让模型永远不敢说任何事情已经完成。

## 37. 效果应该如何评价

### 37.1 本文没有反幻觉实验结果

前面展示的是机制分析与构造反例，不是 Claude Code 的受控准确率评测。独立分析仓库并未为本文提供固定任务集、随机种子、完整运行产物与反幻觉消融。官方产品文档也不能替代这些数据。因此，本节只提出评估协议，不报告任何虚构下降比例，也不据此给产品排名。

一个好的评估首先要固定问题。我们要测的是文件或 API 事实错误、完成声明失真、执行成功率，还是权限越界？它们可能相关，但优化方向不完全一致。系统可以通过拒绝所有任务降低错误行动，却彻底失去实用性；也可以通过少说话降低声明数量，却不提高任务成功率。评价必须同时看收益和代价。

### 37.2 配对设计与环境控制

可设计一组固定仓库快照和任务，每个任务包含明确验收条件、隐藏反例与允许操作范围。比较两种配置时，保持模型、版本、预算、工具环境和初始内容尽量一致，只改变待研究机制。由于模型输出具有随机性，应多次重复，并报告离散程度，而不是只挑选一次成功或失败轨迹。

任务应覆盖不同难度和错误来源：接口版本漂移、相似文件名、搜索范围遗漏、并发文件修改、工具失败、长上下文压缩、外部注入文本、缺失验证脚本和旧测试报告。只用简单算法题，无法测出上下文与工程状态管理的真实价值；只用恶意构造任务，也可能高估日常环境中的风险频率。

### 37.3 指标需要有分母

| 指标 | 建议定义 | 必须同时记录的边界 |
| --- | --- | --- |
| 无依据事实声明率 | 缺少合格支持或与证据冲突的事实声明占比 | 声明提取规则、需要证据的类型 |
| 虚假完成率 | 宣称完成但独立验收不满足的任务占比 | 以全部任务还是完成声明任务为分母 |
| 任务成功率 | 满足预先定义验收的任务占比 | 不得在观察结果后修改验收 |
| 误拦截率 | 合法且可完成动作被错误阻止的占比 | 权限规则和可行性标签 |
| 错误恢复率 | 发生指定故障后正确恢复的任务占比 | 恢复预算、是否引入额外副作用 |
| 证据新鲜度违规率 | 使用不适用历史结果支持当前结论的占比 | 内容与环境指纹范围 |
| 成本与延迟 | Token、模型调用、工具耗时及墙钟时间 | 并发、缓存、等待和基础设施成本 |

若记需要支持的声明集合为 $C$，其中不满足支持标准的集合为 $U$，本文示意的比例为：

$$
R_{\mathrm{unsupported}} = \frac{|U|}{|C|}.
$$

该式只是指标定义，不是原仓库理论。若 $|C|=0$，应报告不适用而不是自动视为完美。还要同时报告声明覆盖率与任务成功率，防止系统通过不回答来获得好看的数值。对虚假完成同样需要明确分母，不能把“完成声明中的错误比例”与“全部任务中的错误比例”混用。

### 37.4 标注与裁判也要审计

无依据声明的标注需要区分事实、推断、建议和不确定性表达。并不是没有引用链接的每句话都是幻觉，普通推理也可能合理；反过来，有链接的错误结论仍然可能缺乏支持。标注者应检查来源是否真正支持相邻断言，以及对象、时间与版本是否一致。

模型裁判可以帮助筛选，但不应成为唯一真值。特别是产品机制评估中，裁判可能偏爱格式完整、措辞专业的答案，而忽略证据链断裂。可采用人工复核、结构化执行结果与争议样本仲裁组合，并报告一致性。评估系统本身也需要避免把自然语言自信当作质量。

### 37.5 消融要考虑机制交互

关闭读取前置检查，并不一定只影响修改安全，还可能改变模型后续搜索行为；增加验证门槛，也可能增加上下文长度和成本。因此，观察到差异时应分析可能的交互，而不是把全部收益归因于一个开关。对于上下文压缩，还应控制任务历史长度与压缩发生时点。

可以分别测试工具取证、文件状态检查、证据恢复和最终验证门槛，再测试组合。但不能因为组合更好，就断言每个模块单独有效；也不能因为某个模块在简单任务中收益小，就否定它在长尾故障中的价值。机制的适用域应当从数据中推导，而不是由设计者预先保证。

### 37.6 发布结果时保留失败轨迹

评估报告应公开任务定义、版本、运行条件、原始结果摘要和失败分类，在隐私允许范围内保留可复核证据。只展示代表性成功案例，会隐藏误拦截、成本上涨和恢复失败。负面结果也有价值，因为它们能说明某种门槛在哪些条件下不值得采用。

本文没有执行上述协议。把协议写清楚，是为了告诉读者未来怎样验证“减少幻觉”的主张，而不是利用实验形式让静态分析看起来像已获得因果证据。

## 38. 机制对照与迁移优先级

### 38.1 不同机制解决不同缺口

纯提示词主要改变模型倾向，工具取证提供外部信息，状态检查约束操作前提，测试验证特定行为，独立审查寻找实现者遗漏。它们不是互相替代的产品功能，而是针对不同失败位置的措施。若不知道错误发生在哪里，简单叠加更多提示、更多工具或更多 Agent，可能只增加成本。

例如 API 名称虚构首先需要目标版本证据，而不是增加任务列表；过时读取需要状态关联，而不是让模型写更长计划；虚假完成需要验证合同，而不是仅给工具更多描述；危险外部指令需要信任边界，而不是扩大检索范围。选择机制前，应把失败路径具体化。

### 38.2 第一优先级：让错误可见

对于从零搭建的 Agent 系统，最值得先做的是工具错误语义、真实结果回传和最终状态区分。若错误被隐藏或统一包装为成功文本，后面的记忆和规划只会建立在错误事实之上。让模型明确看到拒绝、超时和未完成，通常比先构造复杂协作网络更基础。

同时应保证读取对象明确：工具返回路径、版本或必要定位，命令记录工作目录与状态，搜索结果说明范围。这里不是要求所有工具输出巨大元数据，而是保留足以判断适用性的关键字段。没有这些字段，模型再聪明也只能猜测结果对应什么。

### 38.3 第二优先级：把高频错误变成检查

如果团队反复遇到未读文件就修改，可以增加读取前置条件；反复遇到旧测试报告复用，可以绑定内容快照；反复遇到零测试通过，可以验证发现数量。程序检查应针对可明确判定的故障，而不是把一个模糊“质量评分”放到所有路径上。

每个新门槛都应有误拦截与恢复测试。过严规则可能让正常任务无法推进，过宽规则则提供虚假的安全感。更合理的过程是从真实故障出发，定义最小判据，验证正反例，再观察生产使用中的成本与例外。不要因为规则容易写就把它当成正确规则。

### 38.4 第三优先级：管理长期上下文

当任务持续时间和证据量增加，才更需要摘要、长期记忆和渐进式工具加载。这些机制可以降低窗口压力，但必须同时设计恢复路径与过期规则。只增加记忆容量，不管理来源和适用范围，会让错误被保存得更久；只缩短工具结果，不保留定位，会增加重新猜测的机会。

上下文优化应围绕决策需要的信息，而不是单纯追求 Token 最少。失败原因、版本、约束和未验证项往往比冗长成功日志更重要。压缩策略应将这些信息视为高价值状态，并允许模型在关键行动前重新读取原始对象。

### 38.5 最后再增加复杂协作

多 Agent、动态工作流和模型裁判适合处理可拆解、证据丰富、价值足够高的任务。如果单 Agent 连工具状态都无法准确关联，增加协作者只会放大交接问题。应先建立任务合同、产物引用和集成验证，再引入并行，而不是期待并行自动解决可靠性。

协作策略还需要考虑真实独立性。不同检查方法、不同数据视角和独立执行器，比同一模型重复阅读同一摘要更有帮助。角色数量不应成为质量指标。最终仍由整合者解释冲突、验证组合结果并报告剩余风险。

### 38.6 迁移的是原则，不是内部名称

采用者不必复刻社区仓库中的每个类名、feature gate 或提示结构。真正可迁移的，是明确观察、操作、验证和声明之间的接口。内部名称可能随版本变化，原则却能应用于不同工具和模型。本文也不依据静态材料比较 Claude Code 与其他产品谁更可靠，因为那需要前节所述的受控评测。

对于具体团队，可以先选一个重复发生的故障，把它做成回归任务和验收标准。逐步改进比一次性搭建完整“反幻觉平台”更容易得到可信反馈。可靠性工程应该由可观察问题驱动，而不是由功能清单驱动。

## 39. 工程采用清单

### 39.1 工具接口与信任边界

每个工具需要明确名称、参数、返回状态和副作用。只读工具应说明读取范围与截断行为，写入工具应说明覆盖、追加和新建的区别，远程工具应说明授权目标与幂等性。遇到工具未知、参数非法和业务拒绝时，应返回不同错误，避免模型使用同一种盲目重试策略。

外部内容需要在进入上下文时保留来源身份。网页、文件、日志、子 Agent 报告和用户指令不能因为都变成文本就失去区分。对高风险动作，授权应回到可信用户或既定政策，而不是从检索结果中推断。工具接口是可靠性与安全性共同依赖的边界。

### 39.2 证据与新鲜度

检查每个关键结论能否定位到源文件、版本、命令或结果产物。对于当前状态相关结论，确认内容和环境没有发生使证据失效的变化。路径只说明位置，不保证内容不变；时间戳提供线索，不总能替代内容检查；提交哈希固定版本，但不覆盖未提交工作树。

应特别记录失败与未验证项。成功结果容易在摘要中留下，失败条件却更容易被简化成“已处理”。为这类状态设置独立字段，可以减少自然语言压缩带来的歧义。证据恢复也应成为流程的一部分，而不是发生争议后才临时寻找日志。

### 39.3 验证覆盖与失败恢复

把用户目标映射为可观察验收，再为每项选择合适检查。格式、类型、单元、集成、端到端和人工评审的职责不同，不能用最便宜的一项代表全部。原失败场景应优先重跑，因为新增通用测试不一定覆盖用户实际问题。

失败恢复需要区分任务错误、环境错误和检查器错误。不要为解决缺失凭据而改业务逻辑，也不要为使测试变绿而删除有效断言。对于不可重试副作用，先查询实际状态；对于过时读取，先重读并保留他人修改；对于不确定授权，先收缩操作范围。恢复本身也要接受审计。

### 39.4 成本、预算与人类介入

验证有成本，不能假装所有任务都能承受无限测试和多模型审查。应按影响范围、不可逆性和失败代价安排强度。简单文档修改可能只需链接、构建与视觉检查；共享协议变更需要更广覆盖；生产数据操作需要独立授权与恢复方案。成本约束不应被隐藏，而应成为验收设计的输入。

当系统无法取得必要证据时，应明确请求缺失信息或报告未验证项，而不是制造一个看似完整的结论。人类介入的位置也应具体：决定业务取舍、确认权限、评估无法自动判定的效果，而不是要求用户重新完成所有机械检查。

### 39.5 审计与数据治理

记录最小必要证据，避免把密钥、个人数据和整份私有项目无差别复制到长期记忆或跨 Agent 消息。设置访问控制、保留期限和删除流程，并说明脱敏后的证据能够支持什么。需要第三方服务时，应明确发送数据的范围，不能为了“更可靠”而默认扩大外传。

审计记录还应防止被被审查者轻易篡改。对于高风险交付，可让独立执行器生成测试报告，让发布端校验对象与报告关系。对于普通本地任务，未必需要如此强的基础设施，但仍应区分模型自述与工具事实，不把两者存成不可区分的一段摘要。

### 39.6 持续维护而非一次配置

模型、工具、依赖和产品版本都会变化。规则需要回归测试，记忆需要过期，文档需要重新核验，错误分类也应随着真实故障更新。一次配置通过不能证明半年后仍然适用，特别是依赖滚动文档和实验 feature gate 的路径。

团队可以维护一组小而高价值的故障样本：虚构接口、过时锚点、截断日志、错误任务完成、缺失 Hook、零测试和注入文本。每次关键升级重跑这些样本，比仅阅读 release note 更能发现行为回归。本文没有运行这组产品测试，它是从本报告分析中导出的采用建议。

## 40. 局限性、阅读路径与结论

### 40.1 这份报告的证据上限

本文直接阅读的是固定独立分析仓库、公开官方文档与发布信息，不是 Anthropic 完整产品源码。分析仓库中提到的内部路径、变量和函数，均按二手材料定位。即使作者给出了精细解释，本文也不能因此声称独立审计了对应实现，更不能保证当前服务端与历史客户端保持一致。

社区材料的版本断层是重要限制，而不是可以在结论中略去的小注。早期快照、后续章节和黑盒观察提供不同强度的信息。某些机制受开关控制，某些只有工具描述或字符串证据。本文保留这些边界，宁可降低结论强度，也不把不完整材料拼成一套确定、统一、当前默认启用的系统。

### 40.2 机制合理不等于效果已测

读取前置条件、唯一锚点、结构化错误和证据恢复都有清晰工程动机，但本文没有测量它们分别减少多少幻觉。一个机制可能在特定故障上有效，同时增加延迟、误拦截或恢复复杂度。没有受控数据时，应该说它提供了某种约束，而不是说它已经证明总体准确率提升。

同样，模型仍可能读错真实证据、选择错误测试、误解需求或在压缩后丢失关键条件。工具不是万能真值源，测试也不是全部需求的完备证明。可靠性来自多个有限机制互相补足，而不是找到一个可以永久替代判断的模块。

### 40.3 推荐阅读顺序

首先阅读独立仓库的工具系统与编辑策略，理解调用、验证和文件状态的具体接口；随后阅读上下文与记忆章节，观察证据如何进入和离开窗口；再读 Hooks、任务和可观测性，区分提醒、执行与验收；最后阅读较新的 Goal、Workflow 和团队章节，并主动核对其证据类型与版本。

官方运行机制和最佳实践适合建立当前产品的外部使用心智模型，Hooks 与权限文档适合核验具体事件协议。上下文工程与减少幻觉指南提供更一般的方法论。它们的作用不同：官方文档可以确认公开合同，社区分析可以提供实现线索，本文推断则帮助连接工程意义。不要把其中任意一类当成另外两类的替代品。

### 40.4 最值得保留的判断

Claude Code 减少无依据推断的思路，可以概括为让模型更频繁地接触真实对象，让错误调用得到明确反馈，让部分操作依赖可检查前提，让长任务保留恢复线索，并让完成声明面对外部验证。这个概括不需要假定存在一个独立“反幻觉模块”，也不需要把所有安全与编排功能重新命名为反幻觉技术。

最需要避免的误读则是：读过就理解了、定位唯一就改对了、任务完成就测试通过了、多个 Agent 同意就独立验证了、权限允许就结果正确了、上下文保存就证据没有丢失了。每个等号都跨越了一个需要额外证据的层次。

### 40.5 对工程团队的最终建议

先让证据可见、状态准确、错误可恢复，再讨论复杂记忆和自治编排。把最容易被虚构的事实接到真实工具，把最容易被遗漏的验证接到明确流程，把最终声明接到当前对象上的实际结果。对于暂时无法验证的部分，保留未知，而不是用更长解释填补。

这样做并不会让模型不再犯错，却能使错误更早暴露、影响更可控、交付更容易审计。本文认为，这才是从 Claude Code 设计分析中可以迁移的长期价值：不是相信模型会永远诚实准确，而是为它建立一个必须不断面对外部证据的工作环境。
